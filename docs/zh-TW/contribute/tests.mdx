`check` 在每個 pull request 執行，`smoke` 在 merge queue 中、對即將合併的 commit 執行。`full` 每週執行一次。打發行 tag 前，要確認每週執行通過了。各層分工檢查，後續層級會補上前一層沒涵蓋的項目。你也能用 `catalog e2e -tier check|smoke|full` 執行與 CI 相同的測試。

## 開始前

- `check` 不需要 Docker。
- `smoke` 與 `full` 會建立 kind 叢集，需要 Linux 與 Docker。加上 `-cluster current`，就會改用 `KUBECONFIG` 指定的叢集。
- 在 k3s、RKE2 與 KubeSolo 上測試時，發行版會直接安裝在主機上，所以要用一台沒有 Docker、用完就能丟的 Linux 主機，並有 root 權限。每項測試前後都會移除發行版，並清掉 Pod 在主機上留下的掛載、網路介面、路由與防火牆規則。

一般測試使用 `single-node` 或 `multi-node` profile，兩者各有一組設定。

## `check`：檢查每個 pull request

`ci.yml` 會執行下列檢查，每個 job 都是 `nix develop -c scripts/ci/<job>.sh`。在本機用同樣的指令就能執行其中一個。

<Steps>

<Step>

### 執行 Go 測試

執行 Go 測試。

</Step>

<Step>

### 驗證檔案與範本需求

依照各檔案的 schema 驗證所有檔案，並確認兩種 profile 都能解析每個範本的 `requires`。

</Step>

<Step>

### 檢查元件授權

拒絕未經 OSI 核准的元件授權。例外必須同時符合下列條件：

- 授權列在 [`config/licenses.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/licenses.yaml) 的 `optInOnly`。
- 沒有任何 profile 將該元件列為預設啟用（recommended）。

</Step>

<Step>

### 檢查 profile 渲染結果

每種 profile 各渲染兩次，兩次輸出必須完全一致。

接著，針對 [`config/kubernetes.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/kubernetes.yaml) 列出的每個 Kubernetes 版本，用 kubeconform 驗證輸出。自訂資源則依照同次渲染的 CRD 驗證。

</Step>

<Step>

### 檢查範本渲染結果

用測試輸入渲染每個範本，再檢查安全規則、上游 Pod Security 規則與 kubeconform 驗證結果。

</Step>

<Step>

### 交給 API server 驗證

從 [`flake.nix`](https://github.com/zeabur-oss/catalog/blob/main/flake.nix) 啟動 etcd 與 kube-apiserver，使用 Zeabur Installer 固定的 Kubernetes 版本，並只載入渲染出的 CRD。

接著，用 `kubectl apply --dry-run=server` 將兩種 profile 的所有元件與所有範本渲染結果送到 API server。API server 會檢查欄位、預設值、CEL 規則與 Pod Security，不會執行工作負載。

每個範本的 Namespace 都會依照自己的 enforce 等級產生警告。只要出現警告，該範本的測試就會失敗。

</Step>

</Steps>

## `smoke`：安裝變更影響的項目

`ci.yml` 在 merge queue 中會在單節點 amd64 kind 叢集安裝下列項目，再執行煙霧測試（smoke check）：

- 有變更的元件與範本。
- 變更的項目所需要的元件。
- 會安裝變更元件的元件與範本。

排進 merge queue 時，測試的是它和佇列基準 commit 之間的差異，pull request 本身不會啟動 `smoke`。沒有改到任何元件或範本時，沒有東西要測，GitHub 會略過 `smoke` job。請把 `smoke-ok` 設為必要檢查，job 被略過時它會通過，`smoke` job 失敗時它會失敗。

如果多個測試需要相同的相依元件，就會共用叢集。相依元件在每個叢集只安裝一次。元件完成煙霧測試後就會解除安裝，除非同一叢集後續的測試仍需要它。

變更 `config/kubernetes.yaml` 時，`smoke` 會測試所有項目。變更 `tools/`、`go.mod`、`go.sum`、flake、`config/` 的其他檔案或工作流程時，`smoke` 改測 [`config/e2e.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/e2e.yaml) 裡 `smokeRepresentative` 列出的項目。每週的執行仍會測試所有項目。

## `full`：測試資源用量與清理

`weekly.yml` 會呼叫 `e2e.yml`，每週六執行 `full`。打發行 tag 前，確認 `weekly.yml` 在 `main` 最後一次執行通過了。執行的可以是這個 commit，也可以是更早的 commit，只要之後的 commit 都只更新 `measurements/`，或是發行 pull request（`CHANGELOG.md`、`flake.nix` 的版本號、`.changeset/`）。其他情況要先在 `main` 上手動執行一次，通過後再打 tag。

`full` 會在 amd64 與 arm64 上，為每個元件、每種 profile 建立新的 kind 叢集。`single-node` 使用單節點，`multi-node` 使用三節點。

<Steps>

<Step>

### 安裝相依元件

先安裝相依元件，再安裝待測元件。

</Step>

<Step>

### 量測閒置資源用量

每隔 10 秒取樣一次閒置記憶體與 CPU 用量，連續五個樣本一致就停止，最多量測 3 分鐘。

</Step>

<Step>

### 執行健康檢查與煙霧測試，再解除安裝

執行元件的健康檢查與煙霧測試，再解除安裝元件。只要有任何殘留項目，測試就會失敗。

</Step>

</Steps>

### 需要額外憑證的元件

有些元件需要額外的認證資訊，但 CI 沒有這些資訊。[`config/e2e.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/e2e.yaml) 中的 `unready` 列出了這些元件。

`full` 安裝這些元件後，不會等待它們就緒，就會執行煙霧測試並解除安裝。

### 範本與資源預算

`full` 會在單節點 amd64 叢集安裝每個範本及其所需元件，再執行煙霧測試。接著，`full` 會量測範本 Namespace 內各 Pod 閒置時的記憶體與 CPU 用量，取樣方式與前述相同。

元件的量測結果存放在 `measurements/components/<capability>/<upstream>.json`，範本的存放在 `measurements/templates/<id>.json`。`environments` 裡每個環境各有一筆，由 `distribution`、`profile`、`platform`、`kubernetesVersion` 和 `distributionVersion` 指出是哪個環境。`distribution` 是 `kind`、`k3s`、`rke2` 或 `kubesolo`。`distributionVersion` 是裝在主機上的發行版的版本，kind 沒有這個欄位。`result` 是 `passed` 或 `failed`，讀取端遇到其他值一律當作沒有通過。`versions` 列出元件每個 release 的版本，或範本每個映像檔的 tag 與 digest。

```json
{
  "component": "ingress/traefik",
  "environments": [
    {
      "distribution": "k3s",
      "profile": "single-node",
      "platform": {"os": "linux", "architecture": "arm64"},
      "kubernetesVersion": "v1.36.5",
      "distributionVersion": "v1.36.5+k3s1",
      "result": "passed",
      "idle": {"memoryMiB": 22, "cpuMillis": 3},
      "requests": {"memoryMiB": 50},
      "versions": [{"release": "traefik", "version": "41.7.1"}],
      "measuredAt": "2026-11-03"
    }
  ]
}
```

`full` 也會檢查 amd64 上 `single-node` profile 所有預設啟用元件的總用量，確認未超過 [`config/budget.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/budget.yaml) 設定的預算。

`weekly.yml` 會建立 pull request，更新 `measurements/`。你也能手動執行這個工作流程，立即取得量測結果。Renovate 則會針對每個新的上游版本與映像檔 digest 建立 pull request。

### 在 k3s、RKE2 與 KubeSolo 上測試

使用 `-profile k3s`、`-profile rke2` 或 `-profile kubesolo` 時，測試會在 Linux 主機上安裝該發行版，版本固定為 [`config/kubernetes.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/kubernetes.yaml) 指定的版本，並核對每個下載檔的校驗碼。各發行版和預設安裝有這些不同：

- k3s 不啟用內建的 Traefik 與 metrics-server。
- RKE2 不啟用內建的 ingress controller 與 metrics-server，並加裝 local-path-provisioner 當作預設 StorageClass。
- KubeSolo 會另外安裝獨立的 helm-controller。

接著，測試會用 `single-node` 的設定值，對 `single-node` 支援的每個元件執行 `full`。元件的 `distributions` 沒有列出這個發行版時，就不會在上面測試。範本不在這些發行版上測試。

量測結果與 kind 的結果放在一起，`profile` 為 `single-node`，`distribution` 是發行版，`distributionVersion` 是它的版本，例如 `v1.36.5+k3s1`。測試失敗時，該環境會改成 `result: failed`。如果叢集一直沒有回應，這筆就沒有 `kubernetesVersion`。

每個測量環境都有 `sourceDigest`，記錄那次執行裝的元件檔案（範本則是 `template.yaml` 和 `manifests.yaml`）的雜湊值。元件在 `config/kubernetes.yaml` 固定的版本、某個平台上通過測試後，只要元件檔案還是那次執行的內容，`catalog index` 就會把這個發行版連同該平台列進元件的 `testedOn`。元件檔案一改（包括裡面的 release 版本），在新內容通過測試之前就不再列出。之後只要在這個平台上測試失敗，這個平台就會移出清單，等下一次在這個平台上通過再列回來。

## 設定範本測試輸入

範本測試從 [`config/e2e.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/e2e.yaml) 取得輸入值，不需要儲存庫機密，因此 pull request 也會完整執行範本測試。

<Steps>

<Step>

### 設定共用與個別輸入

在 `config/e2e.yaml` 設定：

- `templateInputs`：提供輸入值給所有宣告該輸入的範本。
- `templates.<id>`：設定單一範本的輸入值、測試前要套用到 `templates-e2e-<id>` 的物件，以及要略過哪些煙霧測試和略過的原因。如果輸入值指定了 Secret，也可以在這裡設定，讓測試先套用該 Secret。

所有值都是測試資料，用完即可丟棄。

</Step>

<Step>

### 設定物件儲存測試資料

只要輸入值使用 `.S3`，測試就會在 `templates-e2e-s3` 啟動 SeaweedFS（`object-storage/seaweedfs-operator`）。SeaweedFS 使用測試 CA，並在 TCP 443 提供 HTTPS。備份與物件儲存資料都會送到這裡。

範本 Namespace 內的 `e2e-s3` Secret 會儲存存取認證資訊，以及名為 `ca.crt` 的 CA 憑證。

範本可用 `backupCASecret` 這類選用輸入接收 CA。如果範本無法使用自訂 CA，測試就只會略過與自訂 CA 相關的煙霧測試。

要改用其他儲存服務，請修改 `config/e2e.yaml` 中該範本的輸入值。

</Step>

</Steps>

## 確認結果

`check` 會啟動自己的 API server。`smoke` 與 `full` 會建立自己的 kind 叢集，各自使用獨立的 kubeconfig。

測試結束後，各層級會刪除自己建立的測試環境。加上 `-keep` 可保留環境。

## 遇到問題

| 畫面或結果 | 接著處理 |
| --- | --- |
| `check` 因範本 Namespace 的 Pod Security 警告而失敗 | 依照警告修正範本。警告會讓範本測試失敗。 |
| 元件列在 `unready`，沒有資源量測結果 | 檢查 `config/e2e.yaml`。這些元件需要額外的認證資訊，但 CI 沒有這些資訊，因此測試不量測資源用量。 |
| k3s、RKE2 或 KubeSolo 沒有測試某個元件 | 檢查元件的 `distributions` 是否包含該發行版。 |
| 需要讓節點從映像檔鏡像站拉取映像檔 | 設定 `ZEABUR_REGISTRY_MIRRORS`，值的格式為 `docker.io=http://mirror:5001,ghcr.io=...`。 |
