把元件檔案放在 `components/<capability>/<upstream>.yaml`。每個 capability（用途類別）與上游的組合各用一個檔案。檔案使用 YAML，包含共用外框、安裝內容與設定。路徑就是 ID，例如 `components/ingress/traefik.yaml` 的 ID 是 `ingress/traefik`。

## 共用外框

元件與範本共用 `apiVersion`、`kind`、`metadata` 與 `requires` 這組外框。`kind` 用來區分元件與範本，`requires` 的每一項是 `{capability: <capability>}` 或 `{component: <capability>/<upstream>}`。

```yaml
apiVersion: catalog.zeabur.com/v1
kind: Component                   # or Template
metadata:
  name: Traefik Proxy
  license: MIT                    # SPDX
  homepage: https://traefik.io/traefik/
requires: [{capability: certificates}]   # or {component: <capability>/<upstream>}
```

元件的 `metadata` 還有 `summary`：用一句白話說明它為叢集提供什麼，給挑選元件的人看，翻譯放在 `locales`。檔案開頭的註解說明選用這個元件的原因。

```yaml
metadata:
  summary: Routes traffic from your domains to your services.
  locales:
    zh-TW: {summary: 把網域的流量導向你的服務。}
    zh-CN: {summary: 把域名的流量转发到你的服务。}
```

`locales` 的鍵是 BCP 47 語言標籤。`config/locales.yaml` 列出元件和範本裡每個 `locales` 都要有的語言，`catalog validate` 會檢查。也可以加上其他語言。

## 元件欄位

以下是精簡範例。每個 profile 是一組設定，例如 `single-node` 或 `multi-node`。在 `defaults` 中設定各 profile 是否啟用，填入 `recommended` 表示預設啟用（recommended）。`releases` 按安裝順序列出內容。每個 profile 會先套用共用的 `values`，再合併 `profiles` 中對應的設定。

```yaml
apiVersion: catalog.zeabur.com/v1
kind: Component
metadata:
  name: Traefik Proxy
  license: MIT                    # SPDX; OSI-approved, or opt-in only (see below)
  homepage: https://traefik.io/traefik/
defaults: {single-node: recommended, multi-node: recommended}
requires: [{capability: certificates}]  # installed first
distributions: [k3s, rke2, kubesolo]    # distributions it supports and e2e tests it on
kubeVersion: ">=1.30.0-0"               # Kubernetes versions it supports
replaces: [{component: container-registry/zot}]  # optional, removed components it took over

releases:                         # installed in order
  - name: traefik
    type: helm                                  # helm, manifest or inline
    namespace: traefik
    chart: oci://ghcr.io/traefik/helm/traefik   # or repo: https://… plus chart: <name>
    version: 41.7.1                             # exact; Renovate bumps it
    chartDigest: sha256:…                       # required with chart; see Digests
    values: |                                   # shared by every profile
      gatewayClass:
        # Every value has a comment saying why; `catalog validate` enforces it.
        enabled: true
      image:
        # Every image is <tag>@sha256:<digest>; `catalog render` enforces it.
        tag: v3.7.16@sha256:…
    profiles:                                   # merged over values like helm -f
      single-node: |
        deployment:
          # One node: a second replica gains nothing.
          replicas: 1
  - name: crds
    type: manifest
    namespace: kube-system
    urls: [https://github.com/…/releases/download/{version}/standard-install.yaml]
    version: v1.6.2
    urlDigests: [sha256:…]                      # one per URL, in order
  # or type: inline with manifests: |  objects applied as written

inputs: []        # values to ask for or generate; Secrets are created from them
provides: {...}   # an in-cluster registry other software uses
resources: {...}  # memory it needs while working, on top of idle
internalCRDs: []  # CRDs of detection.crds whose objects it writes itself
networkPolicies: |  # traffic it needs where an installer isolates namespaces
contributes: []   # values added to another component's release (CrowdSec -> Traefik)
detection: {...}  # CRDs, API services, Helm charts, workloads, distribution add-ons
security: {...}   # RBAC summary, podSecurity
health: []        # read-only checks an installer runs on a cluster
smoke: []         # extra e2e checks
leftovers: []     # what the upstream keeps on uninstall (e.g. CRDs)
```

## 安裝工具讀取的欄位

這些欄位告訴安裝工具元件提供什麼，安裝工具不需要靠 ID 認得元件。

`provides.registry` 是叢集裡的 OCI registry：`host` 是映像檔名稱裡的 `host:port`，`ca` 是 Secret key，存放替 registry 簽發憑證的 CA。移除元件前，會等到元件的命名空間以外沒有 Pod 在執行這個 host 的映像檔。

輸入設成 `generate: {type: clusterIP}`，就是替元件的某個 Service 指定固定的 ClusterIP。節點的容器執行環境解析不了 registry 的 host，所以安裝工具會從 Service CIDR 挑一個沒人用的位址填進去，並在每個節點設定 registry mirror 指過去。留空時（CI 就是這樣），Kubernetes 會自動分配位址，只有 Pod 連得到 registry。

```yaml
inputs:
  - name: clusterIp
    release: zot
    path: service.clusterIP
    generate: {type: clusterIP}
provides:
  registry:
    host: zot.zot.svc:5000
    ca: {name: zot-tls, key: ca.crt, namespace: zot}
```

輸入的 `name` 用 camelCase。設成 `generate: {type: random, bytes: 64, encoding: hex}` 的輸入，會產生 `bytes` 個隨機位元組（12 到 64），再用 `encoding` 編碼：小寫 `hex`，或不含填補字元的 `base64url`。這兩個欄位都必填，安裝工具不用猜長度。遇到不認得的 `generate.type`，安裝工具不會替這個輸入填值。

`detection.csiDrivers` 列出元件提供的磁碟區所用的 CSI driver。移除元件前，會等到沒有 PersistentVolume 使用其中任何一個。要找對應的 StorageClass，看它的 `provisioner`。

移除元件前，也會等到它命名空間以外沒有 `detection.crds` 的物件，但 `internalCRDs` 列出的除外：這些 CRD 的物件是元件自己寫的，例如掃描報告。`internalCRDs` 的每一項都必須在 `detection.crds` 裡。

`resources.work` 列出元件會做的每一種工作，例如建置。每一項有 `name`（在清單裡不可重複），再加上下列至少一個欄位，都用 Kubernetes 數量寫 `cpu` 和 `memory`：

- `requests` 和 `limits` 是做一份這種工作的每個 Pod 的資源請求量和上限。工作用的 Pod 由控制器建立、算繪結果裡看不到時（例如建置用的 Pod），就寫這兩個欄位。數值從 chart 的 values 抄過來，升級 chart 時若 values 改了，就跟著改。
- `use` 是元件做一份這種工作時，在閒置用量之外還要多用的資源。閒置用量由 e2e 量測，放在 `index.json`。

```yaml
resources:
  work:
    - name: build
      requests: {cpu: 100m, memory: 256Mi}
      limits: {cpu: "1", memory: 1Gi}
      use: {memory: 500Mi}
```

`catalog index` 把每一項發布到 `index.json` 的 `resources.work`。記憶體以 MiB、CPU 以毫核（millicore）為單位，都無條件進位到整數。該項沒寫的資源不會出現：

```json
"resources": {
  "work": [
    {
      "name": "build",
      "requests": {"memoryMiB": 256, "cpuMillis": 100},
      "limits": {"memoryMiB": 1024, "cpuMillis": 1000},
      "use": {"memoryMiB": 500}
    }
  ]
}
```

排程器看的是請求量，所以安裝工具要把 `requests.memoryMiB` 加進元件量測到的 `requests.memoryMiB`。寫了 `cpu` 和 `memory` 以外的資源，或數量不大於零時，`validate` 會失敗。設定檔（profile）和輸入不會改變結果。

`health` 列出唯讀檢查，讓安裝工具（例如 `zeabur-installer doctor`）檢查已安裝的叢集。每項檢查執行一次 `kubectl wait`，參數寫在 `wait`，等待時間寫在 `timeout`。`wait` 裡要有 `--for` 條件，不要放 `--timeout`。檢查失敗時，安裝工具會顯示 `advice`，用英文告訴使用者該怎麼處理。健康檢查沒有 manifest，也不會套用任何物件。要建立物件的檢查放在 `smoke`，只有 e2e 會執行。e2e 在安裝完成後、執行 `smoke` 之前，先執行 `health`。

```yaml
health:
  - name: nodes-ready
    wait: ["--for=condition=Ready", "nodes.longhorn.io", "--all", "-n", "longhorn-system"]
    timeout: 60s
    advice: "A node that joined without Longhorn needs longhorn: true under join in its configuration. Add it, then run zeabur-installer apply on that node."
```

`distributions` 和 `testedOn` 是兩份不同的清單。元件檔案裡的 `distributions` 列出這個元件支援的發行版，e2e 會在每個發行版上測試它。`index.json` 裡的 `testedOn` 列出測試通過的發行版和通過的平台，例如 `{"distribution": "k3s", "platforms": ["linux/amd64", "linux/arm64"]}`，版本以 `config/kubernetes.yaml` 固定的為準。安裝工具會讀取 `testedOn`，元件要裝在沒列出的發行版和平台上時，提醒使用者它沒測過。`testedOn` 由 `catalog index` 從 `measurements/` 產生，不用手寫。每個元件都有這個欄位，可能是空清單。

`kubeVersion` 是元件支援的 Kubernetes 版本範圍，寫法和 Helm chart 的 `kubeVersion` 相同。填入各 chart 裡最嚴格的範圍，chart 都沒寫時填 `">=1.34.0-0"`。範圍沒有涵蓋 catalog 測試的某個 Kubernetes 版本時，`catalog validate` 會失敗。叢集版本不在範圍內時，安裝工具不會提供這個元件。

`replaces` 列出這個元件接手的舊元件，這些元件已從 catalog 移除，例如 `builds/zeabur-builder` 的 `{component: container-registry/zot}`。設定檔寫了舊 ID 時，安裝工具會請使用者改寫新 ID。現有元件的 ID 不能出現在其他元件的 `replaces` 裡。`catalog validate` 會檢查這一點。完整規則見[安裝工具如何選擇和安裝元件](installers.mdx)。

`contributes` 會把設定值加到另一個元件的 release。`target` 寫出元件和它的 release，`values` 放設定值。

```yaml
contributes:
  - target: {component: ingress/traefik, release: traefik}
    values: |
      ...
```

`detection.addons` 列出發行版自帶、安裝同一個上游的附加元件，例如 k3s 內建的 Traefik 寫成 `{distribution: k3s, name: traefik}`，RKE2 的寫成 `{distribution: rke2, name: rke2-traefik}`。名稱是該附加元件在 `kube-system` 裡的 HelmChart。讀取方遇到不認得的發行版時，略過那一項。

`security.podSecurity` 是元件自己的 namespace 需要的 Pod Security 等級：`restricted`、`baseline` 或 `privileged`。`catalog render` 會用它檢查算繪出的每個 Pod。

`networkPolicies` 給預設擋掉每個命名空間入站流量的安裝工具用。內容是元件自己命名空間裡的標準 NetworkPolicy 物件，這類安裝工具會在安裝 releases 前套用，放行元件需要從其他地方進來的流量。其他安裝工具可以忽略它。`catalog validate` 會檢查每個物件都是元件命名空間裡的 NetworkPolicy。

## 用 digest 固定內容

每個 `releases` 項目都要用 digest 固定內容。如果 chart 或 URL 的內容與 digest 不符，Zeabur Installer 與 `catalog render` 就會停止。

- HTTP chart 的 `chartDigest` 使用儲存庫 `index.yaml` 中對應項目的 `digest`，也就是 `.tgz` 的 sha256。
- OCI chart 的 `chartDigest` 使用 manifest digest，也就是 `helm push` 輸出的值。`helm pull <chart>:<version>@sha256:…` 會檢查這個值。
- `urlDigests` 使用每個下載檔案的 sha256，順序必須與 URL 一致。
- 在 `values` 中，映像檔要使用 `<tag>@sha256:<digest>`，包括 chart 以引數傳給 operator 的映像檔。如果 chart 不接受 digest，就要在 `unpinnedImages` 列出映像檔，並用註解說明原因。URL 安裝項目不受這項要求限制。

Renovate 會一起更新映像檔和 chart 的版本與 digest，但無法讀取 URL 的 digest。Renovate 更新 URL 的 `version` 後，`catalog render` 會失敗，並輸出新的 digest，讓你複製填入。

每次安裝的結果必須一致。chart 不得產生密鑰或憑證。需要產生的值要放在 `inputs`，並儲存在 Secret 中。憑證由 cert-manager 提供。如果兩次渲染的結果不同，`catalog render` 會失敗。

完整欄位定義請見[元件 JSON Schema](https://github.com/zeabur-oss/catalog/blob/main/schema/v1/component.schema.json)。
