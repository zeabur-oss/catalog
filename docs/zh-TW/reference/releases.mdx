---

打上 `vX.Y.Z` tag 後，就會發布 `index.json`、`bundle.tar.gz`、`checksums.txt`，以及 `SHA256SUMS` 和它的 Sigstore 簽章套件。使用 Zeabur Catalog 的工具應固定使用一個版本，驗證後再讀取 `index.json`。1.0 之前，像 0.1 升到 0.2 這樣的更新也可能改變檔案格式，所以請固定使用某個確切版本。

## 版本產物

| 檔案 | 內容 |
| --- | --- |
| `index.json` | 包含所有元件在各個 profile 下的安裝順序與量測資料，以及 Kubernetes 版本。profile 是 `single-node` 或 `multi-node` 的設定組合。 |
| `bundle.tar.gz` | 套件包（bundle），包含索引、交叉檢查資料、元件、範本及相關檔案。 |
| `checksums.txt` | 檔案的檢查碼。 |

`SHA256SUMS` 列出其他每個檔案的雜湊值，並附有 cosign 無金鑰 Sigstore 簽章套件 `SHA256SUMS.sigstore.json`。每個檔案也都有 GitHub 建置來源證明（build provenance attestation）。

所有 zeabur-oss 版本都由 [zeabur-oss/.github](https://github.com/zeabur-oss/.github) 的共用發布工作流程簽署。簽章會記錄該工作流程、儲存庫 `zeabur-oss/catalog` 與 tag。

## 網路上的最新版本

每個不是預發布的版本，也會把 `index.json`、`bundle.tar.gz`、`SHA256SUMS` 和 `SHA256SUMS.sigstore.json` 原封不動複製到 `https://oss-catalog.zeabur.com/v1/`，Zeabur 會從這裡抓範本。`v1` 指的是範本的 `apiVersion`，也就是 `catalog.zeabur.com/v1`。這個網址永遠是最新版本，所以一樣要照上面的方式驗證。每次發版 `SHA256SUMS` 都會變，只看它就能知道有沒有新版本。

## 驗證並讀取版本

<Steps>

<Step>

### 固定版本並驗證簽章

工具先固定要使用的版本，再驗證檔案。先把檔案下載到新建的私有目錄，以下指令驗證 `SHA256SUMS` 的簽章，再核對它列出的檔案：

```sh
tag=vX.Y.Z
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/zeabur-oss/\.github/\.github/workflows/release\.yml@' \
  --certificate-github-workflow-repository zeabur-oss/catalog \
  --certificate-github-workflow-ref "refs/tags/$tag" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
sha256sum --check --ignore-missing SHA256SUMS
```

若要改為檢查來源證明，請執行 `gh attestation verify index.json --repo zeabur-oss/catalog --signer-workflow zeabur-oss/.github/.github/workflows/release.yml`。

</Step>

<Step>

### 讀取索引並產生安裝內容

驗證後，工具讀取 `index.json`。只有不相容的變更才會改動 `indexVersion`。

`catalog` 指出建置這份索引的版本：`version` 是 catalog 的版本，例如 `0.3.0`。`catalog index` 沒帶 `-version` 時（例如在 CI），索引裡沒有 `catalog`。

```json
"catalog": {"version": "0.3.0"}
```

新版本可以替欄位加上新值，不改 `indexVersion`。讀取方遇到不認得的值時照下表處理，遇到不認得的欄位則略過：

| 欄位 | 遇到不認得的值 |
| --- | --- |
| `defaults.<profile>` | 當成 `unsupported`。 |
| `releases[].type`、`security.podSecurity` | 不提供這個元件。 |
| `inputs[].generate.type` | 不替這個輸入填值。需要這個輸入的元件或範本無法安裝。 |
| `distributions`、`testedOn[].distribution`、`detection.addons[].distribution` | 略過這一項。 |
| 測量檔案裡的 `result` | 視為沒通過。 |

`measured` 列出元件測試通過的每個環境。`distribution`（`kind`、`k3s`、`rke2` 或 `kubesolo`）、`profile`、`platform`、`kubernetesVersion` 和 `distributionVersion`（裝在主機上的發行版的版本）指出是哪個環境。`versions` 列出這次執行安裝的每個 release 的版本。

```json
"measured": [
  {
    "distribution": "kind",
    "profile": "single-node",
    "platform": {"os": "linux", "architecture": "amd64"},
    "kubernetesVersion": "v1.36.4",
    "pods": [{"workload": "traefik", "kind": "Deployment", "memoryMiB": 22, "cpum": 3}],
    "versions": [{"release": "traefik", "version": "41.7.1"}],
    "measuredAt": "2026-11-03"
  }
]
```

每個環境都有 `pods`，每個工作負載一列，內容是 `workload` 名稱、`kind`，以及其中一個 Pod 的閒置用量 `memoryMiB` 和 `cpum`，分別取到整數 MiB 和 millicore。工作負載指 Deployment、StatefulSet、DaemonSet 或 Pod，Job 則記在它的控制器底下。這些列計入元件自己的命名空間裡叢集實際跑起來的 Pod，包含由 operator 建立的 Pod。索引不存總量：安裝工具把每一列乘上該工作負載的副本數再加總。副本數與資源請求不量測，要從元件在該 profile 下算繪出的物件讀取；DaemonSet 在每個節點上各跑一個 Pod。排程器依請求量放置 Pod，所以安裝工具會把請求量加總，和節點可分配的記憶體比較。

安裝元件時，工具先執行 `detection`，再根據叢集使用的 profile，提供預設啟用（recommended）的元件。接著，工具向使用者取得各元件的 `inputs`，依 `installOrder` 產生安裝內容，再將 `contributes` 合併到對應目標。挑選元件的規則見[安裝工具如何選擇和安裝元件](installers.mdx)。

部署範本時，工具先檢查叢集是否符合 `requires` 列出的所有需求，再向使用者取得範本輸入值。工具會將其餘自動產生的值寫入 Secret，接著依專案的 Namespace 渲染並套用 `manifests.yaml`。

部署步驟請見[部署範本](../get-started/deploy-a-template.mdx)。

</Step>

</Steps>

## 從 commit 建置版本產物

在任意 commit 執行：

```sh
nix build .#release
```

依照 `flake.nix` 的設定，`release` 會輸出：

- `index.json`
- `crosscheck.json`
- `bundle.tar.gz`
- `checksums.txt`

其中，`bundle.tar.gz` 包含：

- `index.json`
- `crosscheck.json`
- `components/`
- `templates/`
- `schema/`
- `config/`
- `conformance/`
- `measurements/`
- `LICENSE`
- `README.md`

這個指令建置的產物會與發布版本逐位元組相同。工具可以先從尚未發布的 commit 建置產物，等該 commit 發布後，再與已簽章的版本比對。
