Zeabur Catalog 的每個範本都必須符合以下規則。新增或修改範本時，請用 `catalog validate`、`catalog template lint` 與安裝測試檢查其中多項規則，其餘規則則需自行逐項確認。查閱上游文件時，請確認文件版本與範本固定使用的版本完全一致。

## `template.yaml`

- `metadata` 必須列出應用程式名稱、授權、首頁與分類。
- 每個服務都必須指定安全性 profile（`restricted` 或 `baseline`）、資源請求與上限，以及連接埠。服務名稱必須與對應的 Deployment、StatefulSet 或資料庫物件名稱相同。服務的 CPU 與記憶體數值必須是該物件所有容器的總和，連接埠則必須對應容器的具名連接埠。`catalog template lint` 會檢查資源總和與連接埠。
- `security`、`scalability` 與 `upgradeNotes` 必須說明管理者在部署前需要知道的資訊，包括風險與降低風險的措施、副本數範圍與限制增加副本的因素，以及升級所需的步驟。
- `smoke` 必須包含能證明應用程式正常運作的煙霧測試（smoke check），包括資源狀態條件，以及對執行中服務的 HTTP 或 SQL 檢查。
- `requires` 必須以 `<capability>` 或 `<capability>/<upstream>` 列出範本需要的元件。capability 指元件的用途類別。

## 授權與映像檔

- 必須列出應用程式與映像檔的授權。如果軟體採用來源可用授權，必須使用確切的授權名稱，例如 `BUSL-1.1` 或 `SSPL`，並在範本描述中附上授權連結。不得新增要求使用者輸入接受授權字串的輸入欄位。
- 每個映像檔都必須固定到 digest，並在旁邊保留可讀的 tag。這項規則也適用於初始化、遷移與備份映像檔。
- 執行期間不得安裝任何東西，包括使用套件管理工具、下載內容可能變動的程式碼，或在應用程式範本內執行叢集層級的安裝程式。

## Pod 安全性

- 每個容器都必須遵守 [Restricted Pod Security Standard](https://kubernetes.io/docs/concepts/security/pod-security-standards/)，包括初始化容器與 Job 中的容器。容器必須以非 root 使用者執行、設定 `allowPrivilegeEscalation: false`、移除所有 Linux capabilities，並設定 `seccompProfile: RuntimeDefault`。
- 只要應用程式允許，就必須使用唯讀根檔案系統。需要寫入的路徑則必須各自使用專用的可寫入磁碟區。
- 使用 `baseline` 的服務必須提供 `baselineJustification`，列出未符合的控制項並說明原因。不得使用特權容器、主機 Namespace、`hostPath` 或主機連接埠。
- `catalog template lint` 只允許 `net.ipv4.ip_unprivileged_port_start` 與 `net.ipv4.ping_group_range` 這兩個 sysctl，也不允許探針或 hook 設定 host。
- 不得修改 Namespace 的 Pod Security 標籤。
- operator 建立的 Pod 也必須依照相同規則檢查，例如資料庫執行個體與備份 Job。設定時，必須使用 operator 文件列出的欄位。

## 身分識別與 Secret

- 必須設定 `automountServiceAccountToken: false`。除非應用程式需要呼叫 Kubernetes API，否則不得授予 RBAC 權限。所有存取權限都必須限制在該 Namespace 內，且只能存取指定名稱的資源、使用指定的操作動詞。
- 渲染後的資源必須引用 Secret，不得直接包含密碼、金鑰或權杖。自動產生的值必須宣告為 `generate` 輸入，既有認證資訊則必須宣告為必填輸入。
- 每個需要使用者填寫的輸入都必須有簡短的 `label`，並在 `locales` 中提供 `zh-TW` 與 `zh-CN` 的標籤和描述。文字必須寫給部署者看，並使用日常用語。
- `security` 摘要與每項風險的說明，都必須讓第一次自行架設服務的人看得懂。請說清楚會出什麼問題，以及誰會受影響。摘要與每項風險都必須在 `locales` 中提供 `zh-TW` 與 `zh-CN` 內容。
- 必須關閉未經驗證就能存取的管理與除錯端點，以及不安全的首次啟動預設設定。範本必須說明第一位管理員如何登入。

## 網路

- 每個 Pod 都必須加上 `templates.zeabur.com/template: <id>` 標籤。operator 管理的 Pod 必須在自訂資源中設定標籤：CloudNativePG 使用 `inheritedMetadata`，Dragonfly 與 MariaDB 使用 `podMetadata`，Percona 使用 `replsets[].labels`。
- 範本不得附帶預設拒絕流量或針對個別 Pod 的 NetworkPolicy。安裝程式會使用基礎政策隔離不同專案的 Namespace，這就是預設的隔離邊界。
- 沒有登入機制或自身金鑰的元件屬於例外，必須設定 ingress NetworkPolicy，只允許所屬應用程式連入。例如未設定密碼的 Redis 或 Dragonfly、未設定金鑰的 Meilisearch 或 Qdrant，以及執行他人程式碼的沙盒。必須將該服務列在 `security.unauthenticated` 中。`catalog template lint` 會要求提供 ingress NetworkPolicy，且其 `podSelector` 必須指定該服務。`security` 的風險說明必須交代為什麼需要這項政策。執行不受信任程式碼的元件也可以限制對外流量，只允許連往 DNS 與自身的對等服務。
- 除了上述情況，不得限制對外流量。
- 每個 NetworkPolicy，以及其中位於範本 Namespace 內的每個對等端，都必須使用上述標籤選取 Pod。
- 需要在 Namespace 內加強隔離的使用者可以自行新增 NetworkPolicy。例如，下列設定只允許標示 `role=frontend` 的 Pod 連入指定範本的 Pod：

  ```yaml
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata: {name: only-frontend}
  spec:
    podSelector:
      matchLabels: {templates.zeabur.com/template: ghost}
    policyTypes: [Ingress]
    ingress:
    - from: [{podSelector: {matchLabels: {role: frontend}}}]
  ```

- 資料庫、指標與管理介面都必須維持私有存取。只有應用程式能經由 ingress 元件對外公開，並使用 cert-manager 憑證。

## 標籤

- `metadata.version` 必須設為應用程式主要映像檔的 tag。渲染器會在每個渲染後的物件，以及自動產生輸入值的 Secret 上，加上 `app.kubernetes.io/instance: <id>`、`app.kubernetes.io/version: <version>` 與 `templates.zeabur.com/template: <id>`。因此，使用 `kubectl delete <kinds> -l app.kubernetes.io/instance=<id>` 就能從 Namespace 中移除單次安裝的資源。

## 資料與備份

- 必須說明每份狀態資料由誰管理，包括資料庫、上傳檔案、搜尋索引、佇列、設定與加密金鑰。只有遺失也無妨的資料才能使用 `emptyDir`。
- 如果元件中已有對應的資料庫 operator，就必須使用該 operator：PostgreSQL 使用 CloudNativePG，MongoDB 使用 Percona，MariaDB 使用 MariaDB Operator，相容 Redis 的用途使用 Dragonfly Operator。
- 不得在範本中啟用資料庫備份。新安裝的資料庫預設不啟用備份，使用者之後可從 Zeabur 資料庫的 **Backups** 分頁啟用。`upgradeNotes` 必須說明在哪裡啟用備份，以及還原時需要哪些資料庫、檔案、Secret 與金鑰。
- 如果範本有設定備份，必須將備份送到使用 HTTPS 的 S3，啟用 TLS 驗證，並將認證資訊存放在 Secret 中。
- 必須說明刪除應用程式時會保留什麼，以及會刪除什麼。
- 每個 S3 端點的用戶端只要支援自訂 CA，就必須提供選填的 CA 輸入。使用者可提供包含 `ca.crt` 的 Secret，讓用戶端連線到使用私有 CA 的儲存服務。端對端測試會使用這項輸入。資源清單不得包含條件判斷。掛載 Secret 時必須設定 `optional: true`，CA 檔案路徑則必須有獨立的輸入與 `default`。
- `manifests.yaml` 只能使用欄位替換。需要提供選項時，必須使用帶有 `default` 的輸入，不得使用條件判斷。

## 擴充與資源

- 每個容器、Job 與 sidecar 都必須設定 CPU 與記憶體的資源請求和上限。
- 必須說明支援的副本數範圍，以及哪些因素會限制增加副本，例如節點本機磁碟區、內嵌資料庫、存放在記憶體中的工作階段，或只能在單一執行個體上執行的排程器。
- 啟動較慢的服務必須使用啟動探針，並使用就緒探針停止接收流量。存活探針只能用於重新啟動就能修復的狀態。
- 有多個副本的服務必須加上 PodDisruptionBudget。只有支援自動擴充的服務才能啟用自動擴充。

## 升級

- `upgradeNotes` 必須寫出升級順序：備份、遷移、部署更新。也必須說明誰負責執行資料庫結構遷移，以及新舊版本能否同時執行。
- 必須說明哪些情況在回滾到舊版時需要還原資料。回滾映像檔不會撤銷資料庫遷移。
- 共用的 operator 必須經由其元件升級，不得從範本升級。

## 測試

- 煙霧測試會在 CI 的 kind 叢集上執行，並搭配範本需要的元件。在合併到 `main` 後執行的 L1 中，需要相同元件的測試會共用叢集。每晚則使用全新的叢集執行測試。測試必須證明主要功能正常，例如送出經過驗證的請求或執行資料庫查詢，不能只檢查 Pod 是否為 Ready。
- 測試只能使用可拋棄的認證資訊與儲存空間。測試輸入值必須放在 [`config/e2e.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/e2e.yaml)。物件儲存必須使用測試叢集內的 SeaweedFS。
