---
title: Deploy a template with zeaburctl
description: Export a template's objects with zeaburctl, review them, and apply them with kubectl.
---

`zeaburctl templates export` prints the objects that deploying a catalog template into a Zeabur OSS project writes, the same ones the web interface writes. Review them, apply them with `kubectl`, then run the smoke check and your own tests. The [Zeabur OSS docs](https://oss.zeabur.com/docs/zeabur/deploy/templates/) describe the command and a prompt for a coding agent.

## Before you begin

- Install `kubectl` and a `zeaburctl` of the same version as your Zeabur OSS. `zeaburctl` holds the templates of the catalog release that Zeabur OSS bundles.
- Read the license, inputs, `requires`, and security risks in the template's `template.yaml`.
- Use a CNI that enforces NetworkPolicy. Templates don't restrict outbound traffic.
- If the template requires a domain, prepare a cert-manager ClusterIssuer first.
- Install each template only once per project. Object names within a template are fixed.

<Steps>

<Step>

### Check the cluster

Templates don't specify a StorageClass, so volumes use the default. Without a default StorageClass, PersistentVolumeClaims remain `Pending`. List the StorageClasses:

```sh
kubectl get storageclass
```

One line has `(default)` after its name, such as `local-path (default)`. If none does, set a StorageClass as the default before you continue.

</Step>

<Step>

### Export and apply the template

Replace `<id>` with the template ID and `app` with the project:

```sh
umask 077
zeaburctl templates export <id> --project app \
  --domain app.example.com --cluster-issuer letsencrypt --set <name>=<value> > app.yaml
kubectl diff --server-side -f app.yaml
kubectl apply --server-side -f app.yaml
```

Give each input the template asks for with `--set <name>=<value>`. An input you don't give, a missing `--domain` and a missing `--cluster-issuer` appear as `<name>` placeholders: export again with their values before you apply. If the cluster lacks a component that the template requires, `zeaburctl` says so and names the `zeaburctl components export` command that installs it. Prepare object storage buckets and credentials beforehand.

The output starts with the Secrets that hold the template's generated passwords and keys. Each export generates new values, so export once and apply that file. Applying a later export again replaces the passwords of a running application. Don't commit the file to version control.

Check that every pod starts:

```sh
kubectl -n app get pods
```

Within a few minutes, each pod shows `Running` in `STATUS`, and both numbers in `READY` match, such as `1/1`. A pod of a finished Job shows `Completed`. Then run the checks listed under `smoke` in `template.yaml` and your own tests. For a template with a domain:

```sh
curl -sI https://app.example.com | head -n 1
```

The first line is the status line, such as `HTTP/2 200`.

</Step>

<Step>

### Upgrade and roll back

Record the version, project, image references, inputs, and Secret names for each deployment. Before you upgrade, compare the exported objects, read all upgrade notes between the current and target versions, complete a backup, and rehearse the upgrade on a copy.

To roll back the application, check database and storage compatibility first, then apply the objects of a previously verified release. Database downgrades usually require a restore. Store backups outside the application's project.

</Step>

</Steps>

## Generated inputs

Generated inputs include `secret` (`name` and `key`) and a `validation.pattern` that must match the entire generated value.

| Field | Description |
| --- | --- |
| `generate.type` | `random`. |
| `generate.bytes` | Number of random bytes before encoding, from 12 to 64. Required. |
| `generate.encoding` | `base64url` (without padding) or lowercase `hex`. Required. |

User-provided inputs include `required` and don't include generation fields. Encoding 12 bytes as `base64url` produces 16 characters; encoding 16 or 32 bytes as `hex` produces 32 or 64 characters, respectively.

CloudNativePG creates its own Secret for application credentials, and the template reuses it directly.
