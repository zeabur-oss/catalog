description: 了解各层 CI 的运行时机和检查内容，并配置模板测试输入。

`check` 在每个 pull request 中运行，`smoke` 在 merge queue 中、对即将合并的 commit 运行。`full` 在 `main` 收到变更组件或模板的 push 后和每周六运行，只测过期的项目。打发布 tag 前，要确认没有过期的项目。各层分工检查，前一层未覆盖的项目会在后续层级运行。你也可以用 `catalog e2e -tier check|smoke|full` 运行与 CI 相同的测试。

## 开始前

- `check` 不需要 Docker。
- `smoke` 和 `full` 会创建 kind 集群，需要 Linux 和 Docker。加上 `-cluster current`，就会改用 `KUBECONFIG` 指定的集群。
- 在 k3s、RKE2 和 KubeSolo 上测试时，发行版会直接装在主机上，所以要用一台没有 Docker、用完即弃的 Linux 主机，并有 root 权限。每项测试前后都会移除发行版，并清理 Pod 在主机上留下的挂载、网络接口、路由和防火墙规则。

常规测试使用 `single-node` 或 `multi-node` profile，也就是各自的配置组合。

## `check`：检查每个 pull request

`ci.yml` 会运行以下检查，每个 job 都是 `nix develop -c scripts/ci/<job>.sh`。在本地用同样的命令就能运行其中一个。

<Steps>

<Step>

### 运行 Go 测试

运行 Go 测试。

</Step>

<Step>

### 验证文件和模板需求

按照各文件的 schema 验证所有文件，并确认每个模板的 `requires` 都能在两种 profile 下解析。

</Step>

<Step>

### 检查组件许可证

拒绝未经 OSI 批准的组件许可证。例外必须同时满足以下条件：

- 许可证列在 [`config/licenses.yaml`](../../../config/licenses.yaml) 的 `optInOnly` 中。
- 没有任何 profile 将该组件列为默认启用（recommended）。

</Step>

<Step>

### 检查 profile 渲染结果

每种 profile 各渲染两次，两次输出必须完全一致。

接着，针对 [`config/kubernetes.yaml`](../../../config/kubernetes.yaml) 列出的每个 Kubernetes 版本，用 kubeconform 验证输出。自定义资源会按照同次渲染的 CRD 验证。

接着 dry-run 升级和 profile 切换。对每个组件，先把一份渲染结果应用到 API server，再用 `--dry-run=server` 发送另一份：两个 profile 的渲染结果互相替换，以及各 profile 下，PR 基线的渲染结果被这个版本替换。基线是和 `main` 的 merge-base，并用它自己的工具渲染。CRD、Namespace、webhook 配置和 Helm hook 不计入。只要 API server 拒绝更新，例如 `volumeClaimTemplates` 有变化的 StatefulSet，检查就会失败，并指出是哪个组件的哪个对象。Kubernetes 无法原地修改这类字段。

检查失败时，先找有没有能原地更新的改法，例如保持字段原来的值。如果没有，就把 `.changeset/` 里的变更文件标成 `major`，并把迁移步骤写在里面。API server 拒绝升级时，检查会接受，并记为预期的破坏；profile 切换则不接受，所以两个 profile 要用同一个值。

</Step>

<Step>

### 检查模板渲染结果

使用测试输入渲染每个模板，再检查安全规则、上游 Pod Security 规则和 kubeconform 验证结果。

</Step>

<Step>

### 交给 API server 验证

从 [`flake.nix`](../../../flake.nix) 启动 etcd 和 kube-apiserver，使用 Zeabur Installer 固定的 Kubernetes 版本，并且只加载渲染出的 CRD。

接着，用 `kubectl apply --dry-run=server` 将两种 profile 的所有组件和所有模板渲染结果发送到 API server。API server 会检查字段、默认值、CEL 规则和 Pod Security，不会运行工作负载。

每个模板的 Namespace 都会按自身的 enforce 级别生成警告。只要出现警告，该模板的测试就会失败。

</Step>

</Steps>

## `smoke`：安装变更影响的项目

`ci.yml` 在 merge queue 中会在单节点 amd64 kind 集群中安装以下项目，再运行冒烟测试（smoke check）：

- 有变更的组件和模板。
- 变更的项目所需要的组件。
- 会安装变更组件的组件和模板。

进入 merge queue 时，测试的是它和队列基准 commit 之间的差异，pull request 本身不会启动 `smoke`。没有改动任何组件或模板时，没有东西要测，GitHub 会跳过 `smoke` job。请把 `smoke-ok` 设为必需检查，job 被跳过时它会通过，`smoke` job 失败时它会失败。

共用依赖组件的测试会共用集群，依赖组件在每个集群中只安装一次。组件完成冒烟测试后就会卸载，除非同一集群后续的测试仍需要它。

变更 `config/kubernetes.yaml` 时，`smoke` 会测试所有项目。变更 `tools/`、`go.mod`、`go.sum`、flake、`config/` 的其他文件或工作流时，`smoke` 改测 [`config/e2e.yaml`](../../../config/e2e.yaml) 中 `smokeRepresentative` 列出的项目。

## `full`：测试资源用量和清理

`weekly.yml` 会调用 `e2e.yml`，对过期的项目和会安装它的项目运行 `full`。`main` 收到变更 `components/` 或 `templates/` 的 push 后、每周六，以及手动运行时都会跑。手动运行时也可以改为只测指定的 ID（`components`）。

每次运行都会记下它的输入：组件或模板的 `sourceDigest`、先安装的每个组件的 `sourceDigest`（`dependencies`）、主机 profile 安装的每个附加组件的版本（`addOns`），以及 [`config/kubernetes.yaml`](../../../config/kubernetes.yaml) 固定的版本，也就是 kind 节点的 `kubernetesVersion` 或主机发行版的 `distributionVersion`。组件或模板在某个 profile 和架构上，如果还没测过、上次测试失败，或那次运行的输入和现在不同，就算过期。`catalog list -tier full -stale` 会列出运行时要测的项目。

输入无法覆盖所有会影响结果的变更。遇到下面这些情况，要手动运行 `weekly.yml`，并在 `components` 中填入受影响的 ID：

- 上游让某个镜像 tag 或 chart 版本指向新内容。
- `tools/` 中的测试本身有变。
- GitHub runner 镜像更新。

打发布 tag 前，先合并打开着的测量 pull request，再确认对要打 tag 的 commit 运行 `catalog list -tier full -stale` 时，`include` 为空。不为空的话，就在 `main` 上运行 `weekly.yml`，合并它创建的 pull request，再确认一次。

`full` 会在 amd64 和 arm64 上，为每个组件、每种 profile 创建新的 kind 集群。`single-node` 使用单节点，`multi-node` 使用三节点。

<Steps>

<Step>

### 安装依赖组件

先安装依赖组件，再安装待测组件。

</Step>

<Step>

### 测量空闲资源用量

每隔 10 秒采样各 Pod 的空闲内存和 CPU 用量，连续五个样本的总量稳定就停止，最多测量 3 分钟。每个工作负载（Deployment、StatefulSet、DaemonSet、Job 的控制器，或单独的 Pod）只记一条，数值是其中一个 Pod 用量的中位数。总量、副本数和资源请求都不保存，读取的一方从渲染出的对象取得副本数和请求量。

</Step>

<Step>

### 运行健康检查和冒烟测试，再卸载

运行组件的健康检查和冒烟测试，再卸载组件。只要有任何残留项，测试就会失败。

</Step>

</Steps>

### 需要额外凭据的组件

[`config/e2e.yaml`](../../../config/e2e.yaml) 的 `unready` 列出需要 CI 未持有凭据的组件。

`full` 安装这些组件时不等待就绪，接着运行冒烟测试并卸载。

### 模板和资源预算

`full` 会在单节点 amd64 集群中安装每个模板及其需要的组件，运行冒烟测试，再用相同的采样方式测量模板 Namespace 内 Pod 的空闲内存和 CPU 用量。

组件的测量结果存放在 `measurements/components/<id>.json`，模板的存放在 `measurements/templates/<id>.json`。`environments` 里每个环境各有一条，由 `distribution`、`profile`、`platform`、`kubernetesVersion` 和 `distributionVersion` 指明是哪个环境。`distribution` 是 `kind`、`k3s`、`rke2` 或 `kubesolo`。`distributionVersion` 是装在主机上的发行版的版本，kind 没有这个字段。`result` 是 `passed` 或 `failed`，读取方遇到其他值一律当作没有通过。`versions` 列出组件每个 release 的版本，或模板每个镜像的 tag 和 digest。

```json
{
  "component": "traefik",
  "environments": [
    {
      "distribution": "k3s",
      "profile": "single-node",
      "platform": {"os": "linux", "architecture": "arm64"},
      "kubernetesVersion": "v1.36.5",
      "distributionVersion": "v1.36.5+k3s1",
      "result": "passed",
      "pods": [{"workload": "traefik", "kind": "Deployment", "memory": "22Mi", "cpu": "3m"}],
      "versions": [{"release": "traefik", "version": "41.7.1"}],
      "measuredAt": "2026-11-03"
    }
  ]
}
```

`full` 也会检查 amd64 上 `single-node` profile 的默认启用组件总用量，确认符合 [`config/budget.yaml`](../../../config/budget.yaml) 的预算。

`weekly.yml` 会创建或更新同一个 pull request，更新 `measurements/`。每次运行都会保留这个 pull request 里已有的结果，再去掉输入与这次测试的 commit 不同的记录，所以旧文件的结果不会留下来。没测任何项目时则不会改动它。同一时间只会有一个运行。新的运行会取代还在排队的运行，但不会漏掉什么，因为它会重新找出过期的项目。你也可以手动运行这个工作流，立即获取测量结果。Renovate 则会针对每个新的上游版本和镜像 digest 创建 pull request。

### 在 k3s、RKE2 和 KubeSolo 上测试

使用 `-profile k3s`、`-profile rke2` 或 `-profile kubesolo` 时，测试会在 Linux 主机上安装 [`config/kubernetes.yaml`](../../../config/kubernetes.yaml) 固定版本的发行版，并核对每个下载文件的校验和。各发行版和默认安装有这些不同：

- k3s 不启用自带的 Traefik 和 metrics-server。
- RKE2 不启用自带的 ingress controller 和 metrics-server，并加装 local-path-provisioner 作为默认 StorageClass。
- KubeSolo 会另外安装独立的 helm-controller。

接着，测试会使用 `single-node` 的配置值，对 `single-node` 支持的每个组件运行 `full`。组件的 `distributions` 没有列出这个发行版时，就不会在上面测试。模板不在这些发行版上测试。

测量结果与 kind 的结果放在一起，`profile` 为 `single-node`，`distribution` 是发行版，`distributionVersion` 是它的版本，例如 `v1.36.5+k3s1`。测试失败时，该环境会改为 `result: failed`。如果集群一直没有响应，这一条就没有 `kubernetesVersion`。

每个测量环境都有 `sourceDigest`，记录那次运行安装的组件文件（模板则是 `template.yaml` 和 `manifests.yaml`）的哈希值，`dependencies` 则记录先安装的每个组件的 `sourceDigest`。API 在各组件的测量数据旁发布该组件的 `sourceDigest`。只有在某个发行版和平台上通过测试的记录，其哈希值与组件当前的值相同时，安装工具才算这个组件[通过该环境的测试](../reference/installers.mdx#通过测试的环境)。组件文件一改（包括里面的 release 版本），在新文件通过测试之前，都算未通过测试。在某个平台上测试失败后，该平台也算未通过测试，等下一次在该平台上通过才恢复。

## 配置模板测试输入

模板测试从 [`config/e2e.yaml`](../../../config/e2e.yaml) 获取输入值，不需要仓库 secrets，因此 pull request 也会完整运行模板测试。

<Steps>

<Step>

### 配置共享和单独输入

在 `config/e2e.yaml` 中配置：

- `templateInputs`：提供给所有声明该输入的模板。
- `templates.<id>`：提供给单个模板的输入值、测试前要先应用到 `templates-e2e-<id>` 的对象，以及要跳过的冒烟测试和原因。预先应用的对象可以包含输入值指定的 Secret。

所有值都是可丢弃的测试数据。

</Step>

<Step>

### 配置对象存储测试数据

只要输入值使用 `.S3`，测试就会在 `templates-e2e-s3` 启动 SeaweedFS（`seaweedfs-operator`），使用测试 CA，并在 TCP 443 提供 HTTPS。备份和对象存储数据都会发送到这里。

模板 Namespace 内的 `e2e-s3` Secret 会保存访问凭据，以及名为 `ca.crt` 的 CA 证书。

模板使用 `backupCASecret` 这类可选输入接收 CA。无法使用自定义 CA 的模板只会跳过对应的冒烟测试。

要改用其他存储服务，修改 `config/e2e.yaml` 中该模板的输入值。

</Step>

</Steps>

## 确认结果

`check` 会启动自己的 API server；`smoke` 和 `full` 会创建自己的 kind 集群，各自使用独立的 kubeconfig。

测试结束后，各层级会删除自己创建的测试环境。加上 `-keep` 可保留环境。

## 遇到问题

| 界面或结果 | 接下来怎么处理 |
| --- | --- |
| `check` 因模板 Namespace 的 Pod Security 警告而失败 | 按照警告修正模板。警告会让模板测试失败。 |
| 组件列在 `unready`，没有资源测量结果 | 检查 `config/e2e.yaml`。这些组件需要 CI 未持有的凭据，测试不测量资源用量。 |
| k3s、RKE2 或 KubeSolo 没有测试某个组件 | 检查组件的 `distributions` 是否包含该发行版。 |
| 需要让节点从镜像站拉取镜像 | 配置 `ZEABUR_REGISTRY_MIRRORS`，值的格式为 `docker.io=http://mirror:5001,ghcr.io=...`。 |
