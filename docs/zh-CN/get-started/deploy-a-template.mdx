---
title: 用 catalog 命令部署模板
description: 验证版本签名、准备集群，渲染并应用模板，完成部署。
---

验证版本签名后，用 `catalog` 命令渲染并应用一个模板，再运行冒烟测试（smoke check）和你自己的测试，确认部署结果。

如果集群运行着 Zeabur 开源版，改为从**新建** → **应用模板**部署，或用[交给 Agent 安装组件和模板](./agent.mdx)中的提示让 Coding Agent 部署。本页适用于没有 Zeabur 开源版的集群。

## 开始前

- 安装 Go、`git`、`gh`、`cosign`、`kubectl` 和 `sha256sum`（macOS 可从 GNU coreutils 获取）。
- 安装模板 `requires` 列出的每个组件，全部使用同一个版本。
- 使用能落实 NetworkPolicy 的 CNI。安装程序会隔离各项目的 Namespace。模板不限制出站流量。
- 如果模板需要域名，先准备好 cert-manager ClusterIssuer。
- 每个 Namespace 内，同一个模板只能安装一次。模板内的对象名称固定。

<Steps>

<Step>

### 检查集群

模板不指定 StorageClass，卷会使用默认的 StorageClass。没有默认 StorageClass 时，PersistentVolumeClaim 会停留在 `Pending`。列出 StorageClass：

```sh
kubectl get storageclass
```

其中一行的名称后面有 `(default)`，例如 `local-path (default)`。如果没有，先将一个 StorageClass 设为默认再继续。

</Step>

<Step>

### 获取 catalog 命令

把 `vX.Y.Z` 换成你要部署的版本 tag，取出这个 tag 的源码，在其中运行 `catalog` 命令。不要运行未经验证的下载文件。

```sh
tag=vX.Y.Z
git clone --depth 1 --branch "$tag" https://github.com/zeabur-oss/catalog
cd catalog
cargo run -p zeabur-catalog -- check
```

目录没有问题时，`check` 不会输出任何内容，并以状态 0 退出。

</Step>

<Step>

### 验证版本

将同一个版本 tag 的 `bundle.tar.gz`、`SHA256SUMS` 和 `SHA256SUMS.sigstore.json` 下载到新建的私有目录，再按工作流、仓库和 tag 验证 `SHA256SUMS` 的签名，并用它核对 bundle：

```sh
dir=$(mktemp -d)
gh release download "$tag" --repo zeabur-oss/catalog --dir "$dir" \
  --pattern bundle.tar.gz --pattern SHA256SUMS --pattern SHA256SUMS.sigstore.json
(cd "$dir" &&
  cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
    --certificate-identity "https://github.com/zeabur-oss/catalog/.github/workflows/release.yml@refs/tags/$tag" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com &&
  sha256sum --check --ignore-missing SHA256SUMS)
```

`cosign` 会输出 `Verified OK`，`sha256sum` 会输出 `bundle.tar.gz: OK`。只要有一个输出别的内容，就停下来。

只检查签发者或工作流，都会接受其他工作流或其他 zeabur-oss 仓库的签名。签名验证通过后才能解压包（bundle），并拒绝绝对路径、`..` 和链接。

</Step>

<Step>

### 渲染并应用模板

先阅读 `templates/<id>/template.yaml` 中的许可证、输入、`requires` 和安全风险，再渲染对象：

```sh
go run ./tools/cmd/catalog template render -namespace app \
  -domain app.example.com -cluster-issuer letsencrypt -values inputs.json <id> > plan.yaml
```

`inputs.json` 是一个 JSON 对象，以字符串值提供模板要求的输入。对象存储桶和凭证必须提前准备好。

为模板生成包含密码和密钥的 Secret，再应用对象：

```sh
umask 077
go run ./tools/cmd/catalog template inputs -namespace app <id> > secrets.json
kubectl create namespace app
kubectl -n app apply -f secrets.json
kubectl -n app apply -f plan.yaml
```

不要将 `secrets.json` 加入版本控制。每次运行 `inputs` 都会生成新值；每次部署只运行一次，升级时沿用现有的 Secret。

确认每个 Pod 都已启动：

```sh
kubectl -n app get pods
```

几分钟内，每个 Pod 的 `STATUS` 会是 `Running`，`READY` 的两个数字相同，例如 `1/1`。已完成的 Job 的 Pod 显示 `Completed`。接着运行 `template.yaml` 中 `smoke` 列出的检查，以及你自己的测试。模板有域名时：

```sh
curl -sI https://app.example.com | head -n 1
```

第一行是 HTTP 状态行，例如 `HTTP/2 200`。

</Step>

<Step>

### 升级与回滚

记录每次部署的版本、Namespace、镜像引用、输入和 Secret 名称。升级前，比较渲染后的对象差异，阅读当前版本到目标版本之间的所有升级注意事项，完成备份，并先在复制出的环境中演练升级。

要将应用回滚到旧版，先确认数据库和存储的兼容性，再部署此前已验证版本的对象。数据库降级通常需要恢复。备份应存放在应用的 Namespace 之外。

</Step>

</Steps>

## 自动生成的输入

自动生成的输入包含 `secret`（`name` 和 `key`），以及必须匹配完整生成值的 `validation.pattern`。

| 字段 | 说明 |
| --- | --- |
| `generate.type` | `random`。 |
| `generate.bytes` | 编码前的随机字节数，范围为 12 到 64，必填。 |
| `generate.encoding` | `base64url`（不含填充字符）或小写 `hex`，必填。 |

用户提供的输入包含 `required`，不包含自动生成字段。12 个字节以 `base64url` 编码后会得到 16 个字符；16 或 32 个字节以 `hex` 编码后会分别得到 32 或 64 个字符。

CloudNativePG 会自行创建应用凭证的 Secret，模板直接沿用。
