打上 `vX.Y.Z` tag 会发布 `bundle.tar.gz`、`api-v1.tar.gz`、`checksums.txt`，以及 `SHA256SUMS` 和它的 Sigstore 签名包。非预发布版本也会将 API 发布到 `https://oss-catalog.zeabur.com/v1/`。1.0 之前，像 0.1 升到 0.2 这样的更新也可能改变文件格式，需要固定版本时，请指定某个具体版本。

## 版本文件

| 文件 | 内容 |
| --- | --- |
| `api-v1.tar.gz` | 这个版本的 [API](#api)，放在 `v1/` 下。 |
| `bundle.tar.gz` | 软件包（bundle），包含交叉检查数据、组件、模板、schema、一致性测试用例及相关文件。 |
| `checksums.txt` | 两个压缩包的校验和。 |

`SHA256SUMS` 列出其他每个文件的哈希值，并附有 cosign 无密钥 Sigstore 签名包 `SHA256SUMS.sigstore.json`。每个文件也都有 GitHub 构建来源证明（build provenance attestation）。

所有 zeabur-oss 版本都由 [zeabur-oss/.github](https://github.com/zeabur-oss/.github) 的共享发布工作流签名。签名会记录该工作流、仓库 `zeabur-oss/catalog` 和 tag。

## API

API 是一组静态 JSON 文件，保存各组件的声明、渲染结果和 e2e 测量数据，不保存总量或组件通过测试的发行版等计算结果。这些结果由读取工具自行算出，做法见[安装工具如何选择和安装组件](installers.mdx#安装工具要算出的列表)。

| 路径 | 内容 | Schema |
| --- | --- | --- |
| `v1/catalog.json` | 版本的 `version` 和 `commit`、profile、Kubernetes 版本、固定版本的 `distributions`，以及各组件的 `id` 和 `sourceDigest`。 | [`catalog.schema.json`](../../../schema/v1/catalog.schema.json) |
| `v1/components/<id>.json` | 一个组件的 `id`、`sourceDigest`、`declaration`、`render` 和 `measurements`。 | [`component-file.schema.json`](../../../schema/v1/component-file.schema.json) |
| `v1/schema/` | 上面的 schema，以及声明的 schema `component.schema.json`。 | |

Schema 定义数据格式，由 catalog 工具的 Go 类型生成。每个版本的所有文件都通过对应 schema 的检查。

- `declaration` 是[组件文件](component-format.mdx)原有的内容，改用 JSON 表示。
- `sourceDigest` 是组件文件的哈希值。测量记录的 `sourceDigest` 相同，就表示测量的是这个文件。
- `render` 是 `helm template` 在组件支持的各个 profile 下渲染出的内容，使用的 `kubernetesVersion` 是 catalog 测试的最新 Kubernetes 版本。每个 profile 的 `workloads` 列出各 Deployment、StatefulSet 和 DaemonSet 的 `release`、`namespace`、`name`、`kind`、`replicas`，以及 `containers` 和 `initContainers` 的 `requests` 与 `limits`。StatefulSet 另有 `volumeClaimTemplates` 的 `storage`。DaemonSet 没有 `replicas`，在每个节点上各运行一个 Pod。`persistentVolumeClaims` 列出组件渲染出的 PVC 及其 `storage`。
- `measurements` 列出 e2e 运行这个组件的每个环境。

`https://oss-catalog.zeabur.com/v1/` 始终提供 API 主版本 1 的最新版本。如果变更会让读取 `v1` 的工具无法继续使用，就会在另一个路径发布 `v2`，`v1` 则保留最后一个提供它的版本。新版本可以新增字段或值，不必更换主版本。读取工具跳过不认识的字段，遇到不认识的值则按下表处理：

| 字段 | 遇到不认识的值 |
| --- | --- |
| `defaults.<profile>` | 当作 `unsupported`。 |
| `releases[].type`、`security.podSecurity` | 不提供这个组件。 |
| `inputs[].generate.type` | 不为这个输入填值。需要这个输入的组件或模板无法安装。 |
| `distributions`、`detection.addons[].distribution`、测量记录的 `distribution` | 跳过这一项。 |
| 测量记录的 `result` | 视为未通过。 |

每条测量记录用 `distribution`（`kind`、`k3s`、`rke2` 或 `kubesolo`）、`profile`、`platform`、`kubernetesVersion` 和 `distributionVersion` 指明是哪个环境，其中 `distributionVersion` 是装在主机上的发行版版本。`result` 是 `passed` 或 `failed`，`sourceDigest` 是该次运行安装的组件文件哈希值。`versions` 列出该次运行安装的每个 release 的版本。

```json
"measurements": [
  {
    "distribution": "kind",
    "profile": "single-node",
    "platform": {"os": "linux", "architecture": "amd64"},
    "kubernetesVersion": "v1.37.0",
    "result": "passed",
    "sourceDigest": "h1:4RtmKjCcpt+eWwv4Imw1vsdJNJMTxzw/PJ1fBh0+Fzg=",
    "pods": [{"workload": "traefik", "kind": "Deployment", "memory": "22Mi", "cpu": "3m"}],
    "versions": [{"release": "traefik", "version": "41.7.1"}],
    "measuredAt": "2026-11-03"
  }
]
```

通过测试的记录有 `pods`，每个工作负载一行，内容是 `workload` 名称、`kind`，以及其中一个 Pod 的空闲用量 `memory` 和 `cpu`。两者都是 Kubernetes 的数量写法，例如 `22Mi`、`3m`，内存取整到 MiB，CPU 取整到 millicore。工作负载指 Deployment、StatefulSet、DaemonSet 或单独的 Pod，Job 则记在它的控制器名下。这些行涵盖组件自己的 Namespace 里实际运行的 Pod，包括 operator 创建的 Pod。要算总量，就把每一行的用量乘以 `render` 里该工作负载的 `replicas`，再求和。调度器按请求量放置 Pod，所以安装工具会把 `render` 里的内存请求量求和，再和节点可分配的内存比较。

## 验证并读取版本

<Steps>

<Step>

### 固定版本并验证签名

工具先固定要使用的版本，再验证文件。先把文件下载到新建的私有目录，以下命令验证 `SHA256SUMS` 的签名，再核对它列出的文件：

```sh
tag=vX.Y.Z
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/zeabur-oss/\.github/\.github/workflows/release\.yml@' \
  --certificate-github-workflow-repository zeabur-oss/catalog \
  --certificate-github-workflow-ref "refs/tags/$tag" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
sha256sum --check --ignore-missing SHA256SUMS
```

如果要改为检查来源证明，运行 `gh attestation verify api-v1.tar.gz --repo zeabur-oss/catalog --signer-workflow zeabur-oss/.github/.github/workflows/release.yml`。

</Step>

<Step>

### 读取版本并生成安装内容

验证后，工具解压 `api-v1.tar.gz`，按 [API](#api) 的格式读取。

安装组件时，工具执行 `detection`，根据集群的 profile 提供默认启用（recommended）的组件，并向用户获取各组件的 `inputs`。接着按[安装顺序](installers.mdx#安装顺序)生成安装内容，将 `contributes` 合并到对应目标。选择组件的规则见[安装工具如何选择和安装组件](installers.mdx)。

部署模板时，工具检查集群是否满足 `requires` 列出的所有要求，再向用户获取模板输入值，并将其余自动生成的值写入 Secret。接着按项目的 Namespace 渲染并应用 `manifests.yaml`。

部署操作见[部署模板](../get-started/deploy-a-template.mdx)。

</Step>

</Steps>

## 从 commit 构建版本文件

在任意 commit 运行以下命令：

```sh
nix build .#release
go run ./tools/cmd/catalog api -version X.Y.Z -out out/api
```

`nix build .#release` 构建的 `bundle.tar.gz` 包含：

- `crosscheck.json`
- `components/`
- `templates/`
- `schema/`
- `config/`
- `conformance/`
- `measurements/`
- `LICENSE`
- `README.md`

`catalog api` 将 API 写入 `out/api/v1/`，并用对应的 schema 检查每个文件。这个命令会渲染 chart，需要 helm 和网络连接。`bun scripts/release.ts build` 会按发布版本的方式，将 API 打包成 `api-v1.tar.gz`。

这些命令构建的文件会与发布版本逐字节相同。工具可先从尚未发布的 commit 构建文件，等该 commit 发布后，再与已签名的版本比对。
