打上 `vX.Y.Z` tag 会发布 `index.json`、`bundle.tar.gz`、`checksums.txt`，以及 `SHA256SUMS` 和它的 Sigstore 签名包。使用 Zeabur Catalog 的工具应固定一个版本，验证后再读取 `index.json`。1.0 之前，像 0.1 升到 0.2 这样的更新也可能改变文件格式，所以请固定到某个具体版本。

## 版本产物

| 文件 | 内容 |
| --- | --- |
| `index.json` | 所有组件及其各个 profile 的安装顺序与测量数据，以及 Kubernetes 版本。profile 是 `single-node` 或 `multi-node` 的配置组合。 |
| `bundle.tar.gz` | 软件包（bundle），包含索引、交叉检查数据、组件、模板及相关文件。 |
| `checksums.txt` | 文件的校验和。 |

`SHA256SUMS` 列出其他每个文件的哈希值，并附有 cosign 无密钥 Sigstore 签名包 `SHA256SUMS.sigstore.json`。每个文件也都有 GitHub 构建来源证明（build provenance attestation）。

所有 zeabur-oss 版本都由 [zeabur-oss/.github](https://github.com/zeabur-oss/.github) 的共享发布工作流签名。签名会记录该工作流、仓库 `zeabur-oss/catalog` 和 tag。

## 网络上的最新版本

每个不是预发布的版本，也会把 `index.json`、`bundle.tar.gz`、`SHA256SUMS` 和 `SHA256SUMS.sigstore.json` 原样复制到 `https://oss-catalog.zeabur.com/v1/`，Zeabur 会从这里获取模板。`v1` 指的是模板的 `apiVersion`，也就是 `catalog.zeabur.com/v1`。这个地址始终是最新版本，所以同样要按上面的方式验证。每次发版 `SHA256SUMS` 都会变，只看它就能知道有没有新版本。

## 验证并读取版本

<Steps>

<Step>

### 固定版本并验证签名

工具先固定要使用的版本，再验证文件。先把文件下载到新建的私有目录，以下命令验证 `SHA256SUMS` 的签名，再核对它列出的文件：

```sh
tag=vX.Y.Z
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/zeabur-oss/\.github/\.github/workflows/release\.yml@' \
  --certificate-github-workflow-repository zeabur-oss/catalog \
  --certificate-github-workflow-ref "refs/tags/$tag" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
sha256sum --check --ignore-missing SHA256SUMS
```

如果要改为检查来源证明，运行 `gh attestation verify index.json --repo zeabur-oss/catalog --signer-workflow zeabur-oss/.github/.github/workflows/release.yml`。

</Step>

<Step>

### 读取索引并生成安装内容

验证后，工具读取 `index.json`。只有不兼容的变更才会改动 `indexVersion`。

`catalog` 指明构建这份索引的版本：`version` 是 catalog 的版本，例如 `0.3.0`。`catalog index` 没有带 `-version` 时（例如在 CI 中），索引里没有 `catalog`。

```json
"catalog": {"version": "0.3.0"}
```

新版本可以为字段增加新值，而不改 `indexVersion`。读取方遇到不认识的值时按下表处理，遇到不认识的字段则跳过：

| 字段 | 遇到不认识的值 |
| --- | --- |
| `defaults.<profile>` | 当作 `unsupported`。 |
| `releases[].type`、`security.podSecurity` | 不提供这个组件。 |
| `inputs[].generate.type` | 不为这个输入填值。需要这个输入的组件或模板无法安装。 |
| `distributions`、`testedOn[].distribution`、`detection.addons[].distribution` | 跳过这一项。 |
| 测量文件里的 `result` | 视为未通过。 |

`measured` 列出组件测试通过的每个环境。`distribution`（`kind`、`k3s`、`rke2` 或 `kubesolo`）、`profile`、`platform`、`kubernetesVersion` 和 `distributionVersion`（装在主机上的发行版的版本）指明是哪个环境。`versions` 列出这次运行安装的每个 release 的版本。

```json
"measured": [
  {
    "distribution": "kind",
    "profile": "single-node",
    "platform": {"os": "linux", "architecture": "amd64"},
    "kubernetesVersion": "v1.36.4",
    "pods": [{"workload": "traefik", "kind": "Deployment", "memoryMiB": 22, "cpum": 3}],
    "versions": [{"release": "traefik", "version": "41.7.1"}],
    "measuredAt": "2026-11-03"
  }
]
```

每个环境都有 `pods`，每个工作负载一行，内容是 `workload` 名称、`kind`，以及其中一个 Pod 的空闲用量 `memoryMiB` 和 `cpum`，分别取整到整数 MiB 和 millicore。工作负载指 Deployment、StatefulSet、DaemonSet 或 Pod，Job 则记在它的控制器名下。这些行计入组件自己的命名空间里集群实际跑起来的 Pod，包括由 operator 创建的 Pod。索引不存总量：安装工具把每一行乘以该工作负载的副本数再求和。副本数和资源请求不测量，要从组件在该 profile 下渲染出的对象读取；DaemonSet 在每个节点上各跑一个 Pod。调度器按请求量放置 Pod，所以安装工具会把请求量求和，再和节点可分配的内存比较。

安装组件时，工具执行 `detection`，根据集群的 profile 提供默认启用（recommended）的组件，并向用户获取各组件的 `inputs`。接着按 `installOrder` 生成安装内容，将 `contributes` 合并到对应目标。选择组件的规则见[安装工具如何选择和安装组件](installers.mdx)。

部署模板时，工具检查集群是否满足 `requires` 列出的所有要求，再向用户获取模板输入值，并将其余自动生成的值写入 Secret。接着按项目的 Namespace 渲染并应用 `manifests.yaml`。

部署操作见[部署模板](../get-started/deploy-a-template.mdx)。

</Step>

</Steps>

## 从 commit 构建版本产物

在任意 commit 执行：

```sh
nix build .#release
```

根据 `flake.nix`，`release` 输出包含：

- `index.json`
- `crosscheck.json`
- `bundle.tar.gz`
- `checksums.txt`

其中，`bundle.tar.gz` 包含：

- `index.json`
- `crosscheck.json`
- `components/`
- `templates/`
- `schema/`
- `config/`
- `conformance/`
- `measurements/`
- `LICENSE`
- `README.md`

这个命令会构建与发布版本逐字节相同的产物。工具可先从尚未发布的 commit 构建，等该 commit 发布后，再与已签名的版本比对。
