组件在整个集群只安装一次，所有项目共用。模板则是每个项目各自安装，同一个模板可以装很多次。

每个组件放在自己的目录 `components/<id>/component.yaml`，每个上游各用一个目录。目录里只放 `component.yaml` 和组件的 README。`component.yaml` 使用 YAML，包含通用结构、安装内容和配置。目录名就是 ID，例如 `components/traefik/component.yaml` 的 ID 是 `traefik`。ID 只用小写英文字母、数字和单个连字符，也不会和任何模板的 ID 相同。

## 通用结构

组件与模板共用 `apiVersion`、`kind`、`metadata` 和 `requires` 这组结构。`kind` 用来区分组件与模板，`requires` 的每一项是 `{capability: <capability>}` 或 `{component: <id>}`。

```yaml
apiVersion: catalog.zeabur.com/v1
kind: Component                   # or Template
metadata:
  name: Traefik Proxy
  license: MIT                    # SPDX
  homepage: https://traefik.io/traefik/
requires: [{capability: certificates}]   # or {component: <id>}
```

组件的 `metadata` 还有 `summary`：用一句平实的话说明它为集群提供什么，给挑选组件的人看，翻译放在 `locales`。文件开头的注释说明选用这个组件的原因。`license` 里的 `LicenseRef-` 许可证要在 `licenseUrls` 写上许可证全文的 HTTPS 网址，例如 `licenseUrls: {LicenseRef-example: https://example.com/license}`，读取端才能放上链接。

```yaml
metadata:
  summary: Routes traffic from your domains to your services.
  locales:
    zh-TW: {summary: 把網域的流量導向你的服務。}
    zh-CN: {summary: 把域名的流量转发到你的服务。}
```

`locales` 的键是 BCP 47 语言标签。`config/locales.yaml` 列出组件和模板里每个 `locales` 都必须包含的语言，`zeabur-catalog check` 会检查。也可以加上其他语言。

## README

每个组件目录里有 `README.md`、`README.zh-TW.md` 和 `README.zh-CN.md`，写给要决定装不装它的管理员。只能用这些二级标题，并按这个顺序：`## 简介`、`## 安装前准备`、`## 使用方法`、`## 移除`、`## 故障排除`（英文是 `Introduction`、`Before you install`、`Use it`、`Remove it`、`Troubleshooting`；繁体中文是 `簡介`、`安裝前準備`、`使用方式`、`移除`、`疑難排解`）。

- **简介**（必填）说明组件做什么、集群什么时候需要它，以及它的权限范围有多大。
- **安装前准备**说明要在集群外准备什么，例如存储桶和它的密钥。有输入设了 `required`、又没有 `default` 和 `generate` 时必填。
- **使用方法**（必填）链接到 Zeabur 开源版文档里会用到这个组件的页面，不重复那页的内容。Zeabur 开源版没有对应界面的组件，写出第一步，并链接到上游文档。
- **移除**（必填）说明移除会删除什么、会保留什么，以及要先确认什么。
- **故障排除**（选填）每个问题一个 `###`。

`zeabur-catalog check` 会检查文件和标题。

## 组件字段

下面是一个精简示例。`defaults` 指定各 profile（`single-node` 或 `multi-node` 的配置组合）的启用配置，`recommended` 表示默认启用（recommended）。`releases` 列出按顺序安装的内容，`profiles` 的配置会合并到共用的 `values`。

```yaml
apiVersion: catalog.zeabur.com/v1
kind: Component
metadata:
  name: Traefik Proxy
  license: MIT                    # SPDX; OSI-approved, or opt-in only (see below)
  homepage: https://traefik.io/traefik/
provides: {capability: ingress}         # the capability it offers; see below for registry
defaults: {single-node: recommended, multi-node: recommended}
requires: [{capability: certificates}]  # installed first
distributions: [k3s, rke2, kubesolo]    # distributions it supports and e2e tests it on
kubeVersion: ">=1.30.0-0"               # Kubernetes versions it supports

releases:                         # installed in order
  - name: traefik
    type: helm                                  # helm, manifest or inline
    namespace: traefik
    chart: oci://ghcr.io/traefik/helm/traefik   # or repo: https://… plus chart: <name>
    version: 42.1.3                             # exact; Renovate bumps it
    chartDigest: sha256:…                       # required with chart; see Digests
    values: |                                   # shared by every profile
      gatewayClass:
        # Every value has a comment saying why; `zeabur-catalog check` enforces it.
        enabled: true
      image:
        # Every image is <tag>@sha256:<digest>; `zeabur-catalog render` enforces it.
        tag: v3.7.16@sha256:…
    profiles:                                   # merged over values like helm -f
      single-node: |
        deployment:
          # One node: a second replica gains nothing.
          replicas: 1
  - name: crds
    type: manifest
    namespace: kube-system
    urls: [https://github.com/…/releases/download/{version}/standard-install.yaml]
    version: v1.6.3
    urlDigests: [sha256:…]                      # one per URL, in order
  # or type: inline with manifests: |  objects applied as written

inputs: []        # values to ask for or generate; Secrets are created from them
resources: {...}  # memory it needs while working, on top of idle
internalCRDs: []  # CRDs of detection.crds whose objects it writes itself
networkPolicies: |  # traffic it needs where an installer isolates namespaces
contributes: []   # values added to another component's release (CrowdSec -> Traefik)
detection: {...}  # CRDs, API services, Helm charts, workloads, distribution add-ons
security: {...}   # RBAC summary, podSecurity
health: []        # read-only checks an installer runs on a cluster
smoke: []         # extra e2e checks
leftovers: []     # what the upstream keeps on uninstall (e.g. CRDs)
```

## 安装工具读取的字段

这些字段告诉安装工具组件提供什么，安装工具不需要靠 ID 认出组件。

`provides.capability` 是组件提供的 capability（用途类别），例如 `ingress` 或 `logs`。`requires` 写 `{capability: <capability>}` 时，会安装提供这个 capability 的其中一个组件。不提供 capability 的组件不写这个字段，`requires` 要用 `{component: <id>}` 指定它。安装工具读取 `enable` 和 `disable` 里的名称时先当作组件 ID，所以 capability 不能和另一个提供其他 capability 的组件 ID 相同。

`provides.registry` 是集群里的 OCI registry：`host` 是镜像名称里的 `host:port`，`ca` 是 Secret key，存放为 registry 签发证书的 CA。移除组件前，会等到其命名空间以外没有 Pod 在运行这个 host 的镜像。

输入设成 `generate: {type: clusterIP}`，就是给组件的某个 Service 指定固定的 ClusterIP。节点的容器运行时解析不了 registry 的 host，所以输入留空时，Zeabur 安装组件时会从 Service CIDR 选一个空闲地址填进去。让每个节点连到这个地址由组件自己负责，Zeabur Builder 用一个 DaemonSet 处理。不经过 Zeabur 安装时（CI 就是这样），输入保持为空，Kubernetes 会自动分配地址，只有 Pod 能访问 registry。

```yaml
inputs:
  - name: clusterIp
    release: zot
    path: service.clusterIP
    generate: {type: clusterIP}
provides:
  capability: builds
  registry:
    host: zot.zot.svc:5000
    ca: {name: zot-tls, key: ca.crt, namespace: zot}
```

输入的 `name` 使用 camelCase。设为 `generate: {type: random, bytes: 64, encoding: hex}` 的输入，会生成 `bytes` 个随机字节（12 到 64），再用 `encoding` 编码：小写 `hex`，或不含填充字符的 `base64url`。这两个字段都必填，安装工具无需猜测长度。遇到不认识的 `generate.type`，安装工具不会为这个输入填值。

输入的值会写到某个 release 配置值里的 `path`，或写进 `secret` 指定的 Secret 的某个 key，这个 Secret 由安装工具在安装前创建。`testValue` 是 CI 安装时用的值。

`detection.csiDrivers` 列出组件提供的卷所用的 CSI driver。移除组件前，会等到没有 PersistentVolume 使用其中任何一个。要找对应的 StorageClass，看它的 `provisioner`。

移除组件前，也会等到其命名空间以外没有 `detection.crds` 的对象，但 `internalCRDs` 列出的除外：这些 CRD 的对象是组件自己写的，例如扫描报告。`internalCRDs` 的每一项都必须在 `detection.crds` 里。

`resources.work` 列出组件会做的每一种工作，例如构建。每一项有 `name`（在列表里不能重复），再加上下列至少一个字段，都用 Kubernetes 数量写 `cpu` 和 `memory`：

- `requests` 和 `limits` 是做一份这种工作的每个 Pod 的资源请求量和上限。工作用的 Pod 由控制器创建、渲染结果里看不到时（例如构建用的 Pod），就写这两个字段。数值从 chart 的 values 抄过来，升级 chart 时如果 values 改了，就跟着改。
- `use` 是组件做一份这种工作时，在空闲用量之外还要多用的资源。空闲用量由 e2e 测量，发布在 [API](releases.mdx#api)。

```yaml
resources:
  work:
    - name: build
      requests: {cpu: 100m, memory: 256Mi}
      limits: {cpu: "1", memory: 1Gi}
      use: {memory: 500Mi}
```

API 原样发布 `resources.work`。调度器看的是请求量，所以安装工具要把 `requests` 的内存用量加进组件渲染出的对象里 Pod 的请求量。写了 `cpu` 和 `memory` 以外的资源，或数量不大于零时，`validate` 会失败。profile 和输入不会改变结果。

`health` 列出只读检查，供安装工具检查已安装的集群。每项检查会在 `timeout` 指定的时间内，等待 `resource` 指定的对象满足 `condition` 条件。`Deployment`、`DaemonSet` 和 `StatefulSet` 的检查没有 `condition`，也不能用 `all`，这些对象在 rollout 完成时就算就绪。`resource` 要填写 `kind`，该类型有命名空间时还要填写 `namespace`，并且必须从以下三种方式中选一种：用 `name` 指定单个对象、用 `selector` 指定标签匹配的对象，或用 `all: true` 指定该类型的所有对象。`kind` 不在 [schema](../../../schema/v1/component.schema.json) 列出的类型中，或缺少必填字段时，`validate` 会失败。检查失败时，安装工具会先显示对象的原因和消息，再显示 `advice`，用英文告诉用户该怎么处理。健康检查没有 manifest，也不会应用任何对象。需要创建对象的检查放在 `smoke`，只有 e2e 会运行。e2e 在安装完成后、运行 `smoke` 之前，先运行 `health`。 每个 `smoke` 检查有 `wait` 列表。每一项用 `resource: <kind>/<name>` 指定对象，或用类型加上 `selector` 或 `all: true` 指定，该类型有命名空间时还要填写 `namespace`。每一项要填写 `condition`，格式是 `condition=<name>` 或 `jsonpath=<path>=<value>`；`Deployment`、`DaemonSet` 和 `StatefulSet` 不用填，rollout 完成就算就绪。

提供 admission webhook（`ValidatingWebhookConfiguration` 或 `MutatingWebhookConfiguration`）的组件至少要有一项 `health` 检查，这样需要它的组件才会等 webhook 能响应后再安装。没有的话，`zeabur-catalog render` 会失败。

```yaml
health:
  - name: nodes-ready
    resource: {kind: Node.longhorn.io, all: true, namespace: longhorn-system}
    condition: Ready
    timeout: 60s
    advice: "The message above names what the node lacks for Longhorn, such as open-iscsi, an NFS client or a kernel module. Install it on that node; the check passes once Longhorn finds it."
```

`distributions` 列出组件支持的发行版，e2e 会在每个发行版上测试它。通过测试的环境是另一个列表，由安装工具根据 API 的测量数据算出，做法见[安装工具如何选择和安装组件](installers.mdx#通过测试的环境)。组件在某个发行版和平台上没有通过测试时，安装工具会提示用户。

`kubeVersion` 是组件支持的 Kubernetes 版本范围，写法与 Helm chart 的 `kubeVersion` 相同。填写各 chart 中最严格的范围，chart 都没写时填 `">=1.34.0-0"`。范围没有覆盖 catalog 测试的某个 Kubernetes 版本时，`zeabur-catalog check` 会失败。集群版本不在范围内时，安装工具不会提供这个组件。

`persistsData: true` 表示组件把状态存在卷里，移除它会丢失这些数据。

带 `skipIfPresent` 的 release，在列出的 CRD 全都已经存在时会跳过，例如集群上已有其他安装装好的 Gateway API CRD。`releaseName` 用在 Helm release 名称与 `name` 不同的时候。

`contributes` 会把配置值加到另一个组件的 release。`target` 写明组件和它的 release，`values` 放配置值。组件本身要有一个 `helm` release：安装工具靠 Helm release 找出自己装过的组件，每次写入目标时再把它们的配置值加回去。

```yaml
contributes:
  - target: {component: traefik, release: traefik}
    values: |
      ...
```

`detection` 的其他列表用来找出集群上已经装好的同一个上游，让安装工具直接沿用：`crds` 和 `apiServices` 按名称匹配，`ingressControllers` 和 `gatewayControllers` 按 IngressClass 或 GatewayClass 的 controller 匹配，`helmCharts` 按 Helm release 的 chart 匹配，`workloads` 按 Deployment、StatefulSet 或 DaemonSet 的 `kind` 和 `labels` 匹配。

`detection.addons` 列出发行版自带、安装同一个上游的附加组件，例如 k3s 内置的 Traefik 写成 `{distribution: k3s, name: traefik}`，RKE2 的写成 `{distribution: rke2, name: rke2-traefik}`。名称是该附加组件在 `kube-system` 里的 HelmChart。读取方遇到不认识的发行版时，跳过那一项。

`security.podSecurity` 是组件自己的 namespace 需要的 Pod Security 级别：`restricted`、`baseline` 或 `privileged`。`zeabur-catalog render` 会用它检查渲染出的每个 Pod。

`networkPolicies` 给默认拦截每个命名空间入站流量的安装工具用。内容是组件自己命名空间里的标准 NetworkPolicy 对象，这类安装工具会在安装 releases 前应用，放行组件需要从其他地方进来的流量。其他安装工具可以忽略它。`zeabur-catalog check` 会检查每个对象都是组件命名空间里的 NetworkPolicy。

## 用 digest 固定内容

每个 `releases` 条目都要用 digest 固定内容。chart 或 URL 的内容与 digest 不符时，`zeabur-catalog render` 会停止，安装工具也必须停止。

- HTTP chart 的 `chartDigest` 使用仓库 `index.yaml` 中对应条目的 `digest`，也就是 `.tgz` 的 sha256。
- OCI chart 的 `chartDigest` 使用 manifest digest，也就是 `helm push` 输出的值。`helm pull <chart>:<version>@sha256:…` 会检查这个值。
- `urlDigests` 使用每个下载文件的 sha256，顺序必须与 URL 一致。
- 镜像在 `values` 中使用 `<tag>@sha256:<digest>`，也包括 chart 通过参数传给 operator 的镜像。chart 无法接受 digest 时，要在 `unpinnedImages` 中列出镜像，并用注释说明原因。URL 安装条目不受这项要求限制。

Renovate 会一起更新镜像和 chart 的版本与 digest，但无法读取 URL 的 digest。Renovate 更新 URL 的 `version` 后，`zeabur-catalog render` 会失败，并输出新的 digest，供你复制填入。

安装结果必须一致：chart 不得生成密钥或证书。需要生成的值放在 `inputs` 中，并存储在 Secret 中；证书由 cert-manager 提供。如果两次渲染的结果不同，`zeabur-catalog render` 会失败。

完整字段定义见[组件 JSON Schema](../../../schema/v1/component.schema.json)。
