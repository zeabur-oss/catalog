---
title: Template standards
description: Follow the template standards when adding or updating Zeabur Catalog templates, and check security, networking, data, upgrades, and test configuration.
---

Every template in Zeabur Catalog must follow these rules. When you add or update a template, use `catalog validate`, `catalog template lint`, and installation tests to check the rules those tools cover, then review the remaining rules individually. When you consult upstream documentation, check the exact version pinned in the template.

## `template.yaml`

- `metadata` must list the application name, license, homepage, and category.
- Every service must specify a security profile (`restricted` or `baseline`), resource requests and limits, and ports. The service name must match the corresponding Deployment, StatefulSet, or database object name. The service's CPU and memory values must equal the totals across all containers in that object, and its ports must match the containers' named ports. `catalog template lint` checks resource totals and ports.
- `security`, `scalability`, and `upgradeNotes` must cover what administrators need to know before deployment: risks and mitigations, the supported replica range and constraints on adding replicas, and the steps required to upgrade.
- `smoke` must include smoke checks that prove the application works, including resource status conditions and HTTP or SQL checks against the running service.
- `requires` must list the components the template needs as `<capability>` or `<capability>/<upstream>`. A capability identifies a component's functional category.

## Licenses and images

- You must list the licenses for the application and its images. For source-available software, use the exact license name, such as `BUSL-1.1` or `SSPL`, and include a license link in the template description. Don't add an input that asks users to enter a license acceptance string.
- You must pin every image to a digest and keep a readable tag alongside it. This rule also applies to initialization, migration, and backup images.
- Don't install anything at runtime. This includes using package managers, downloading code whose contents can change, or running cluster-level installers from an application template.

## Pod security

- Every container must follow the [Restricted Pod Security Standard](https://kubernetes.io/docs/concepts/security/pod-security-standards/), including init containers and containers in Jobs. Containers must run as a non-root user, set `allowPrivilegeEscalation: false`, drop all Linux capabilities, and set `seccompProfile: RuntimeDefault`.
- When the application supports it, use a read-only root filesystem and provide dedicated writable volumes for paths that need writes.
- Services that use `baseline` must provide a `baselineJustification` that identifies the controls they don't meet and explains why. Don't use privileged containers, host namespaces, `hostPath`, or host ports.
- `catalog template lint` permits only the `net.ipv4.ip_unprivileged_port_start` and `net.ipv4.ping_group_range` sysctls and rejects probes or hooks that set a host.
- Don't modify the Namespace's Pod Security labels.
- Check Pods that operators create, such as database instances and backup Jobs, against the same rules. Configure them with the fields listed in the operator's documentation.

## Identity and Secrets

- You must set `automountServiceAccountToken: false`. Don't grant RBAC permissions unless the application needs to call the Kubernetes API. All permissions must be limited to named resources and operation verbs within that Namespace.
- Rendered resources must reference Secrets and must not contain passwords, keys, or tokens directly. Declare automatically generated values as `generate` inputs and existing credentials as required inputs.
- Every input that users must fill in must have a short `label`, with `zh-TW` and `zh-CN` labels and descriptions in `locales`. Write for the person deploying the application, and use everyday language.
- The `security` summary and each risk must use language that first-time self-hosters can understand. Explain what can go wrong and who it affects. Provide `zh-TW` and `zh-CN` content for the summary and each risk in `locales`.
- You must disable management and debug endpoints that permit unauthenticated access, along with insecure first-start defaults. The template must explain how the first administrator signs in.

## Networking

- Every Pod must have the `templates.zeabur.com/template: <id>` label. For operator-managed Pods, configure labels in the custom resource: use `inheritedMetadata` for CloudNativePG, `podMetadata` for Dragonfly and MariaDB, and `replsets[].labels` for Percona.
- Templates must not include default-deny or per-Pod NetworkPolicies. The installer uses base policies to isolate project Namespaces from one another. This is the default isolation boundary.
- Components without a login mechanism or their own key are exceptions. They must have an ingress NetworkPolicy that permits connections only from their application. Examples include Redis or Dragonfly without a password, Meilisearch or Qdrant without a key, and sandboxes that execute other people's code. List the service in `security.unauthenticated`; `catalog template lint` requires an ingress NetworkPolicy whose `podSelector` selects that service. The risk description in `security` must explain why this policy exists. Components that execute untrusted code can also restrict outbound traffic to DNS and their own peers.
- Don't restrict outbound traffic outside the cases above.
- Every NetworkPolicy, and every peer within it that resides in the template's Namespace, must select Pods with the label above.
- Users who need stronger isolation within a Namespace can add their own NetworkPolicies. For example, the following configuration permits only Pods labeled `role=frontend` to connect to the specified template's Pods:

  ```yaml
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata: {name: only-frontend}
  spec:
    podSelector:
      matchLabels: {templates.zeabur.com/template: ghost}
    policyTypes: [Ingress]
    ingress:
    - from: [{podSelector: {matchLabels: {role: frontend}}}]
  ```

- Databases, metrics, and management interfaces must remain private. Only applications may be publicly exposed through an ingress component, and they must use cert-manager certificates.

## Labels

- `metadata.version` must match the tag of the application's main image. The renderer adds `app.kubernetes.io/instance: <id>`, `app.kubernetes.io/version: <version>`, and `templates.zeabur.com/template: <id>` to every rendered object and to Secrets for automatically generated input values. This lets `kubectl delete <kinds> -l app.kubernetes.io/instance=<id>` remove a single installation's resources from the Namespace.

## Data and backups

- You must explain who manages each piece of stateful data, including databases, uploaded files, search indexes, queues, configuration, and encryption keys. Use `emptyDir` only for data that can be lost.
- When the components include a matching database operator, you must use it: CloudNativePG for PostgreSQL, Percona for MongoDB, MariaDB Operator for MariaDB, and Dragonfly Operator for Redis-compatible use cases.
- Don't enable database backups in templates. Backups are disabled by default for newly installed databases. Users can enable them later from the **Backups** tab of their Zeabur database. `upgradeNotes` must explain where to enable backups and which databases, files, Secrets, and keys a restore requires.
- If a template configures backups, it must send them to S3 over HTTPS, enable TLS verification, and store credentials in Secrets.
- You must explain what remains and what gets deleted when users delete the application.
- For each S3 endpoint, if the client supports a custom CA, you must provide an optional CA input. Use a Secret containing `ca.crt` to support storage services that use a private CA. End-to-end tests use this input. Manifests must not contain conditionals: set `optional: true` when mounting the Secret, and provide a separate input with a `default` for the CA file path.
- `manifests.yaml` must use only field substitution. When users need a choice, use inputs with a `default`, not conditionals.

## Scaling and resources

- Every container, Job, and sidecar must have CPU and memory requests and limits.
- You must describe the supported replica range and constraints on adding replicas, such as node-local volumes, embedded databases, in-memory sessions, or single-instance schedulers.
- Services that start slowly must use startup probes and readiness probes to stop receiving traffic. Use liveness probes only for states that a restart can fix.
- Services with multiple replicas must have a PodDisruptionBudget. Enable autoscaling only for services that support it.

## Upgrades

- `upgradeNotes` must state the upgrade order: back up, migrate, and deploy the update. It must also explain who runs database schema migrations and whether old and new versions can run at the same time.
- You must explain when rolling back to an older version requires a data restore. Rolling back an image doesn't undo database migrations.
- Upgrade shared operators through their components, not through templates.

## Tests

- Smoke tests run on kind clusters in CI with the components the template requires. In L1, which runs after merges to `main`, tests that need the same components share a cluster; nightly runs use fresh clusters. Tests must prove that core functionality works, such as by sending an authenticated request or running a database query. Checking only whether Pods are Ready isn't enough.
- Tests must use only disposable credentials and storage. Put test input values in [`config/e2e.yaml`](https://github.com/zeabur-oss/catalog/blob/main/config/e2e.yaml). Object storage must use SeaweedFS in the test cluster.
