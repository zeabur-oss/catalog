A component is installed once for the whole cluster and used by every project. A template, in contrast, is installed per project and can be installed many times.

Place component files in `components/<id>.yaml`, with one file for each upstream. Each YAML file contains the shared envelope, installation content, and configuration. The file name is the ID. For example, `components/traefik.yaml` has the ID `traefik`. An ID is lowercase letters, digits and single hyphens, and no template has the same ID.

## Shared envelope

Components and templates share an envelope of `apiVersion`, `kind`, `metadata`, and `requires`. `kind` distinguishes components from templates. Each entry of `requires` is `{capability: <capability>}` or `{component: <id>}`.

```yaml
apiVersion: catalog.zeabur.com/v1
kind: Component                   # or Template
metadata:
  name: Traefik Proxy
  license: MIT                    # SPDX
  homepage: https://traefik.io/traefik/
requires: [{capability: certificates}]   # or {component: <id>}
```

A component's `metadata` also has a `summary`: what it gives the cluster, in one plain sentence for people choosing components, with its translations in `locales`. A comment at the top of the file says why the catalog recommends the component.

```yaml
metadata:
  summary: Routes traffic from your domains to your services.
  locales:
    zh-TW: {summary: 把網域的流量導向你的服務。}
    zh-CN: {summary: 把域名的流量转发到你的服务。}
```

The keys of `locales` are BCP 47 tags. `config/locales.yaml` lists the tags that every `locales` map in components and templates must have, and `catalog validate` checks them. A map may have other tags too.

## Component fields

The following example shows a minimal component. `defaults` specifies whether to enable the component for each profile (the `single-node` or `multi-node` configuration), and `recommended` means enabled by default (recommended). `releases` lists the content to install in order. Settings in `profiles` merge into the shared `values`.

```yaml
apiVersion: catalog.zeabur.com/v1
kind: Component
metadata:
  name: Traefik Proxy
  license: MIT                    # SPDX; OSI-approved, or opt-in only (see below)
  homepage: https://traefik.io/traefik/
provides: {capability: ingress}         # the capability it offers; see below for registry
defaults: {single-node: recommended, multi-node: recommended}
requires: [{capability: certificates}]  # installed first
distributions: [k3s, rke2, kubesolo]    # distributions it supports and e2e tests it on
kubeVersion: ">=1.30.0-0"               # Kubernetes versions it supports

releases:                         # installed in order
  - name: traefik
    type: helm                                  # helm, manifest or inline
    namespace: traefik
    chart: oci://ghcr.io/traefik/helm/traefik   # or repo: https://… plus chart: <name>
    version: 41.7.1                             # exact; Renovate bumps it
    chartDigest: sha256:…                       # required with chart; see Digests
    values: |                                   # shared by every profile
      gatewayClass:
        # Every value has a comment saying why; `catalog validate` enforces it.
        enabled: true
      image:
        # Every image is <tag>@sha256:<digest>; `catalog render` enforces it.
        tag: v3.7.16@sha256:…
    profiles:                                   # merged over values like helm -f
      single-node: |
        deployment:
          # One node: a second replica gains nothing.
          replicas: 1
  - name: crds
    type: manifest
    namespace: kube-system
    urls: [https://github.com/…/releases/download/{version}/standard-install.yaml]
    version: v1.6.2
    urlDigests: [sha256:…]                      # one per URL, in order
  # or type: inline with manifests: |  objects applied as written

inputs: []        # values to ask for or generate; Secrets are created from them
resources: {...}  # memory it needs while working, on top of idle
internalCRDs: []  # CRDs of detection.crds whose objects it writes itself
networkPolicies: |  # traffic it needs where an installer isolates namespaces
contributes: []   # values added to another component's release (CrowdSec -> Traefik)
detection: {...}  # CRDs, API services, Helm charts, workloads, distribution add-ons
security: {...}   # RBAC summary, podSecurity
health: []        # read-only checks an installer runs on a cluster
smoke: []         # extra e2e checks
leftovers: []     # what the upstream keeps on uninstall (e.g. CRDs)
```

## What installers read

These fields tell an installer what a component offers, so the installer never needs to know a component by its ID.

`provides.capability` is the capability the component offers, such as `ingress` or `logs`. A `requires` entry `{capability: <capability>}` installs one of the components that offer it. A component that offers no capability leaves it out, and `requires` names it with `{component: <id>}`. A capability isn't the ID of a component that offers another capability, because an installer reads a name in `enable` and `disable` as a component ID first.

`provides.registry` is an OCI registry in the cluster: `host` is the `host:port` images name, and `ca` is the Secret key with the CA that signs its certificate. Removing the component waits until no Pod outside its namespaces runs an image from the host.

An input with `generate: {type: clusterIP}` takes a fixed ClusterIP for a Service of the component. A node's container runtime cannot resolve the registry host, so an installer fills the input with a free address in the Service CIDR and points a registry mirror on each node there. Left empty, as in CI, Kubernetes assigns an address and only Pods reach the registry.

```yaml
inputs:
  - name: clusterIp
    release: zot
    path: service.clusterIP
    generate: {type: clusterIP}
provides:
  capability: builds
  registry:
    host: zot.zot.svc:5000
    ca: {name: zot-tls, key: ca.crt, namespace: zot}
```

An input's `name` is camelCase. An input with `generate: {type: random, bytes: 64, encoding: hex}` takes `bytes` random bytes, from 12 to 64, in `encoding`: lowercase `hex` or `base64url` without padding. Both fields are required, so an installer never guesses a length. An installer doesn't fill in an input whose `generate.type` it doesn't know.

`detection.csiDrivers` lists the CSI drivers of the volumes the component provides. Removing the component waits until no PersistentVolume uses one of them. Find the StorageClass by its `provisioner`.

Removing a component also waits for the objects of its `detection.crds` outside its namespaces, except those in `internalCRDs`: CRDs whose objects the component writes itself, such as scan reports. Every entry of `internalCRDs` must be in `detection.crds`.

`resources.work` lists each kind of work the component does, such as a build. Each entry has a `name`, unique in the list, and one or more of these, each in Kubernetes quantities of `cpu` and `memory`:

- `requests` and `limits` are the resource requests and limits of each pod doing one unit of the work. Give them when a controller creates those pods and no render shows them, such as a build pod. Copy them from the chart's values, and change them when a chart upgrade changes those values.
- `use` is what the component uses on top of its idle use while doing one unit of the work. Its idle use is measured in e2e and published in `index.json`.

```yaml
resources:
  work:
    - name: build
      requests: {cpu: 100m, memory: 256Mi}
      limits: {cpu: "1", memory: 1Gi}
      use: {memory: 500Mi}
```

`catalog index` publishes each entry under `resources.work` in `index.json`, with memory in whole MiB and CPU in whole millicores, both rounded up. A resource that the entry doesn't give is left out:

```json
"resources": {
  "work": [
    {
      "name": "build",
      "requests": {"memoryMiB": 256, "cpuMillis": 100},
      "limits": {"memoryMiB": 1024, "cpuMillis": 1000},
      "use": {"memoryMiB": 500}
    }
  ]
}
```

An installer adds `requests.memoryMiB` to the requests of the pods in the component's rendered objects, because the scheduler counts requests. `validate` fails on a resource other than `cpu` and `memory`, or on an amount that is not above zero. Profiles and inputs don't change the result.

`health` lists read-only checks that an installer such as `zeabur-installer doctor` runs on an installed cluster. Each check runs `kubectl wait` once, with the arguments in `wait` and the time limit in `timeout`. Put a `--for` condition in `wait`, and leave out `--timeout`. When a check fails, the installer shows its `advice`, which tells the reader in English what to do. A health check has no manifest and applies nothing. Put checks that create objects in `smoke`, which only e2e runs. e2e runs `health` after install and before `smoke`.

```yaml
health:
  - name: nodes-ready
    wait: ["--for=condition=Ready", "nodes.longhorn.io", "--all", "-n", "longhorn-system"]
    timeout: 60s
    advice: "A node that joined without Longhorn needs longhorn: true under join in its configuration. Add it, then run zeabur-installer apply on that node."
```

`distributions` and `testedOn` are two different lists. `distributions` in the component file names the distributions the component supports, and e2e tests it on each of them. `testedOn` in `index.json` lists each distribution where that test passed, at the release that `config/kubernetes.yaml` pins, on the current component file, with the platforms it passed on, such as `{"distribution": "k3s", "platforms": ["linux/amd64", "linux/arm64"]}`. An installer reads `testedOn` to warn that a component is untested on a distribution and platform it doesn't list. `catalog index` derives `testedOn` from `measurements/`, so don't write it by hand. It's present on every component and can be empty.

`kubeVersion` is the range of Kubernetes versions the component supports, in the syntax of a Helm chart's `kubeVersion`. Give the strictest range of its charts, or `">=1.34.0-0"` when they give none. `catalog validate` fails when the range leaves out a Kubernetes version that the catalog tests. An installer doesn't offer the component on a cluster outside the range.

`contributes` adds values to a release of another component. `target` names the component and its release, and `values` holds the values.

```yaml
contributes:
  - target: {component: traefik, release: traefik}
    values: |
      ...
```

`detection.addons` lists the add-ons of a distribution that install the same upstream, such as `{distribution: k3s, name: traefik}` for the Traefik that k3s packages and `{distribution: rke2, name: rke2-traefik}` for RKE2's. The name is the add-on's HelmChart in `kube-system`. A reader ignores an entry of a distribution it doesn't know.

`security.podSecurity` is the Pod Security level that the component's own namespaces need: `restricted`, `baseline` or `privileged`. `catalog render` checks every Pod of the render against it.

`networkPolicies` is for installers that block incoming traffic to each namespace by default. It holds standard NetworkPolicy objects in the component's own namespaces, which such an installer applies before the releases, for the traffic the component needs from elsewhere. Other installers can ignore it. `catalog validate` checks that each object is a NetworkPolicy in one of the component's namespaces.

## Pin content with digests

Every `releases` entry must pin its content with a digest. Zeabur Installer and `catalog render` stop if the chart or URL content doesn't match its digest.

- For HTTP charts, `chartDigest` uses the `digest` from the corresponding entry in the repository's `index.yaml`, which is the sha256 of the `.tgz`.
- For OCI charts, `chartDigest` uses the manifest digest, which is the value that `helm push` outputs. `helm pull <chart>:<version>@sha256:…` checks this value.
- `urlDigests` uses the sha256 of each downloaded file, in the same order as the URLs.
- Images in `values` use `<tag>@sha256:<digest>`, including images that the chart passes to an operator as arguments. If a chart doesn't accept a digest, list the image in `unpinnedImages` and explain why in a comment. URL installation entries are exempt from this requirement.

Renovate updates image and chart versions together with their digests. It can't read digests for URLs: after Renovate updates their `version`, `catalog render` fails and outputs the new digest for you to copy into the file.

Installation results must be consistent: charts must not generate keys or certificates. Put values that need generation in `inputs` and store them in Secrets; cert-manager supplies certificates. If two renders produce different results, `catalog render` fails.
