title: Releases and bundles
description: Pin a Zeabur Catalog version, verify Sigstore signatures, and read index.json, or build release artifacts from a specific commit.
---

Pushing a `vX.Y.Z` tag publishes `index.json`, `bundle.tar.gz`, `checksums.txt`, and `SHA256SUMS` with its Sigstore signature bundle. Tools that use Zeabur Catalog should pin a version and verify it before reading `index.json`. Before 1.0, a minor release can change the file format, so pin an exact release.

## Release artifacts

| File | Contents |
| --- | --- |
| `index.json` | All components, with their installation order and measurements for each profile, and the Kubernetes versions. A profile is a configuration for `single-node` or `multi-node`. |
| `bundle.tar.gz` | A bundle containing the index, cross-check data, components, templates, and related files. |
| `checksums.txt` | File checksums. |

`SHA256SUMS` lists the checksum of every other file and has a cosign keyless Sigstore signature bundle, `SHA256SUMS.sigstore.json`. Every file also has a GitHub build provenance attestation.

The shared release workflow of [zeabur-oss/.github](https://github.com/zeabur-oss/.github) signs every zeabur-oss release. A signature names that workflow, the repository `zeabur-oss/catalog`, and the tag.

## The latest release on the web

Each release that is not a pre-release also copies `index.json`, `bundle.tar.gz`, `SHA256SUMS` and `SHA256SUMS.sigstore.json`, unchanged, to `https://oss-catalog.zeabur.com/v1/`. Zeabur fetches its templates from there. `v1` is the template `apiVersion`, `catalog.zeabur.com/v1`. The address always has the latest release, so verify it as above. `SHA256SUMS` changes with every release, so you can tell from it alone whether there is a new one.

## Verify and read a release

<Steps>

<Step>

### Pin a version and verify the signature

The tool first pins the version to use, then verifies the file. The following commands verify the signature of `SHA256SUMS`, then the files it lists. Download the files into a new private directory first:

```sh
tag=vX.Y.Z
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/zeabur-oss/\.github/\.github/workflows/release\.yml@' \
  --certificate-github-workflow-repository zeabur-oss/catalog \
  --certificate-github-workflow-ref "refs/tags/$tag" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
sha256sum --check --ignore-missing SHA256SUMS
```

To check the attestation instead, run `gh attestation verify index.json --repo zeabur-oss/catalog --signer-workflow zeabur-oss/.github/.github/workflows/release.yml`.

</Step>

<Step>

### Read the index and generate installation content

After verification, the tool reads `index.json`. Only incompatible changes affect `indexVersion`.

`catalog` names the release that built the index: `version` is the catalog version, such as `0.3.0`. An index that `catalog index` writes without `-version`, such as in CI, has no `catalog`.

```json
"catalog": {"version": "0.3.0"}
```

A newer release can add a value to a field without a new `indexVersion`. A reader handles a value it doesn't know as follows, and ignores a field it doesn't know:

| Field | A value the reader doesn't know |
| --- | --- |
| `defaults.<profile>` | Treat it as `unsupported`. |
| `releases[].type`, `security.podSecurity` | Don't offer the component. |
| `inputs[].generate.type` | Don't fill in the input. A component or template that needs the input can't be installed. |
| `distributions`, `testedOn[].distribution`, `detection.addons[].distribution` | Ignore the entry. |
| `result` in a measurement file | The run didn't pass. |

`measured` lists each environment where the component's test passed. `distribution` (`kind`, `k3s`, `rke2` or `kubesolo`), `profile`, `platform`, `kubernetesVersion` and `distributionVersion`, the release of a distribution on the host, name the environment. `versions` gives the version of each release that the run installed.

```json
"measured": [
  {
    "distribution": "kind",
    "profile": "single-node",
    "platform": {"os": "linux", "architecture": "amd64"},
    "kubernetesVersion": "v1.36.4",
    "idle": {"memoryMiB": 22, "cpuMillis": 3},
    "requests": {"memoryMiB": 50},
    "versions": [{"release": "traefik", "version": "41.7.1"}],
    "measuredAt": "2026-11-03"
  }
]
```

Each environment has `idle`, what the component uses, and `requests`, what its pods request. Each has `memoryMiB` and `cpuMillis`, rounded to whole numbers, and leaves out a resource it doesn't give. `requests` has only `memoryMiB` for now. The scheduler places pods by requests, so an installer compares the sum of `requests.memoryMiB` with a node's allocatable memory. Both come from the same full tier run and count the pods in the component's own namespaces as the cluster runs them, including pods that an operator creates.

When installing components, the tool runs `detection`, offers the components enabled by default (recommended) for the cluster's profile, and collects each component's `inputs` from the user. It then generates installation content according to `installOrder` and merges `contributes` into the corresponding targets. [How installers choose and install components](installers.mdx) gives the rules for choosing them.

When deploying a template, the tool checks that the cluster meets all requirements listed in `requires`, collects template inputs from the user, and writes the remaining automatically generated values to a Secret. It then renders and applies `manifests.yaml` for the project's Namespace.

For deployment instructions, see [Deploy a template](../get-started/deploy-a-template.mdx).

</Step>

</Steps>

## Build release artifacts from a commit

Run this command at any commit:

```sh
nix build .#release
```

As defined in `flake.nix`, the `release` output includes:

- `index.json`
- `crosscheck.json`
- `bundle.tar.gz`
- `checksums.txt`

The `bundle.tar.gz` file contains:

- `index.json`
- `crosscheck.json`
- `components/`
- `templates/`
- `schema/`
- `config/`
- `conformance/`
- `measurements/`
- `LICENSE`
- `README.md`

This command builds artifacts that are byte-for-byte identical to the release artifacts. Tools can build from an unreleased commit, then compare the artifacts with the signed release after that commit is released.
