Pushing a `vX.Y.Z` tag publishes `bundle.tar.gz`, `api-v1.tar.gz`, `checksums.txt`, and `SHA256SUMS` with its Sigstore signature bundle. Each release that isn't a pre-release also publishes its API at `https://oss-catalog.zeabur.com/v1/`. Before 1.0, a minor release can change the file format, so pin an exact release when you need one.

## Release files

| File | Contents |
| --- | --- |
| `api-v1.tar.gz` | The [API](#the-api) of this release, under `v1/`. |
| `bundle.tar.gz` | A bundle containing cross-check data, components, templates, schemas, conformance cases and related files. |
| `checksums.txt` | Checksums of the two archives. |

`SHA256SUMS` lists the checksum of every other file and has a cosign keyless Sigstore signature bundle, `SHA256SUMS.sigstore.json`. Every file also has a GitHub build provenance attestation.

The shared release workflow of [zeabur-oss/.github](https://github.com/zeabur-oss/.github) signs every zeabur-oss release. A signature names that workflow, the repository `zeabur-oss/catalog`, and the tag.

## The API

The API is static JSON files. It holds facts: what each component declares, what it renders, and what e2e measured. It doesn't hold values worked out from them, such as totals or the distributions a component passed on. A reader works those out, as [How installers choose and install components](installers.mdx#what-the-installer-works-out) describes.

| Path | Contents | Schema |
| --- | --- | --- |
| `v1/catalog.json` | The release's `version` and `commit`, the profiles, the Kubernetes versions, the pinned `distributions` and each component's `id` and `sourceDigest`. | [`catalog.schema.json`](../../schema/v1/catalog.schema.json) |
| `v1/components/<id>.json` | One component: its `id` and `sourceDigest`, its `declaration`, its `render` and its `measurements`. | [`component-file.schema.json`](../../schema/v1/component-file.schema.json) |
| `v1/schema/` | The schemas above, and `component.schema.json`, the schema of a declaration. | |

The schemas are the contract, and the Go types of the catalog's tools generate them. Each file of a release passes its schema.

- `declaration` is the [component file](component-format.mdx) as written, as JSON.
- `sourceDigest` is the digest of the component file. A measurement with the same `sourceDigest` measured this file.
- `render` is what `helm template` renders for each profile the component supports, at `kubernetesVersion`, the newest Kubernetes version the catalog tests. For each profile, `workloads` lists each Deployment, StatefulSet and DaemonSet with its `release`, `namespace`, `name`, `kind`, `replicas`, and the `requests` and `limits` of its `containers` and `initContainers`. A StatefulSet also has the `storage` of its `volumeClaimTemplates`. A DaemonSet has no `replicas`; it runs one pod on each node. `persistentVolumeClaims` lists the claims the component renders with their `storage`.
- `measurements` lists each environment where e2e ran the component.

`https://oss-catalog.zeabur.com/v1/` always holds the latest release of API major version 1. A change that would break a reader of `v1` comes with `v2`, at its own path, and `v1` then keeps the last release that had it. A newer release can add a field or a value without a new major version. A reader ignores a field it doesn't know, and handles a value it doesn't know as follows:

| Field | A value the reader doesn't know |
| --- | --- |
| `defaults.<profile>` | Treat it as `unsupported`. |
| `releases[].type`, `security.podSecurity` | Don't offer the component. |
| `inputs[].generate.type` | Don't fill in the input. A component or template that needs the input can't be installed. |
| `distributions`, `detection.addons[].distribution`, a measurement's `distribution` | Ignore the entry. |
| A measurement's `result` | The run didn't pass. |

Each measurement names its environment with `distribution` (`kind`, `k3s`, `rke2` or `kubesolo`), `profile`, `platform`, `kubernetesVersion` and `distributionVersion`, the release of a distribution on the host. `result` is `passed` or `failed`, and `sourceDigest` is the digest of the component file that the run installed, and `dependencies` the `sourceDigest` of each component that the run installed before it, by ID. `addOns` gives the pinned release of each add-on that the run installed on the host, by name. `versions` gives the version of each release that the run installed.

```json
"measurements": [
  {
    "distribution": "kind",
    "profile": "single-node",
    "platform": {"os": "linux", "architecture": "amd64"},
    "kubernetesVersion": "v1.36.4",
    "result": "passed",
    "sourceDigest": "h1:4RtmKjCcpt+eWwv4Imw1vsdJNJMTxzw/PJ1fBh0+Fzg=",
    "pods": [{"workload": "traefik", "kind": "Deployment", "memory": "22Mi", "cpu": "3m"}],
    "versions": [{"release": "traefik", "version": "41.7.1"}],
    "measuredAt": "2026-11-03"
  }
]
```

A passing run has `pods`, one row for each workload: its `workload` name, its `kind`, and the idle `memory` and `cpu` of one pod of it. Both are Kubernetes quantities such as `22Mi` and `3m`, rounded to whole MiB and millicores. A workload is a Deployment, StatefulSet, DaemonSet, or bare Pod, or the controller of a Job. The rows cover the pods in the component's own namespaces as the cluster ran them, including pods that an operator creates. To get a total, multiply each row by the workload's `replicas` in `render` and add them up. The scheduler places pods by requests, so an installer compares the sum of the memory requests in `render` with a node's allocatable memory.

## Verify and read a release

<Steps>

<Step>

### Pin a version and verify the signature

The tool first pins the version to use, then verifies the file. The following commands verify the signature of `SHA256SUMS`, then the files it lists. Download the files into a new private directory first:

```sh
tag=vX.Y.Z
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/zeabur-oss/\.github/\.github/workflows/release\.yml@' \
  --certificate-github-workflow-repository zeabur-oss/catalog \
  --certificate-github-workflow-ref "refs/tags/$tag" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
sha256sum --check --ignore-missing SHA256SUMS
```

To check the attestation instead, run `gh attestation verify api-v1.tar.gz --repo zeabur-oss/catalog --signer-workflow zeabur-oss/.github/.github/workflows/release.yml`.

</Step>

<Step>

### Read the release and generate installation content

After verification, the tool unpacks `api-v1.tar.gz` and reads it as [the API](#the-api).

When installing components, the tool runs `detection`, offers the components enabled by default (recommended) for the cluster's profile, and collects each component's `inputs` from the user. It then generates installation content according to the [install order](installers.mdx#install-order) and merges `contributes` into the corresponding targets. [How installers choose and install components](installers.mdx) gives the rules for choosing them.

When deploying a template, the tool checks that the cluster meets all requirements listed in `requires`, collects template inputs from the user, and writes the remaining automatically generated values to a Secret. It then renders and applies `manifests.yaml` for the project's Namespace.

For deployment instructions, see [Deploy a template](../get-started/deploy-a-template.mdx).

</Step>

</Steps>

## Build the release files from a commit

Run these commands at any commit:

```sh
nix build .#release
go run ./tools/cmd/catalog api -version X.Y.Z -out out/api
```

`nix build .#release` builds `bundle.tar.gz`, which contains:

- `crosscheck.json`
- `components/`
- `templates/`
- `schema/`
- `config/`
- `conformance/`
- `measurements/`
- `LICENSE`
- `README.md`

`catalog api` writes the API to `out/api/v1/` and checks each file against its schema. It renders the charts, so it needs helm and the network. `bun scripts/release.ts build` packs it into `api-v1.tar.gz` the same way a release does.

These commands build files that are byte-for-byte identical to the release files. Tools can build from an unreleased commit, then compare the files with the signed release after that commit is released.
